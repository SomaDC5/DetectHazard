## 1. まず、差が有意かどうか

検証F1の**上位10エポックの幅**を見ると、条件間の差より大きい。

| 条件 | ベスト検証F1 | エポック | 上位10エポックの幅 |
|---|---|---|---|
| FinalFusion_SAM_APM | 0.6691 | 48 | 0.0053 |
| FinalFusion_SAM_APM_InstLoss（p=0.5） | 0.6701 | 28 | 0.0043 |
| FinalFusion_SAM_APM_InstLoss_p10（p=1.0） | 0.6665 | 49 | 0.0029 |

**3条件の差（0.001〜0.004）は、1回の学習の中のエポック間ゆらぎ（0.003〜0.005）より小さい。**
テスト側の箇所F値の差はもう少し大きいが、「どのエポックが検証F1のくじに当たったか」に
相当左右されている。

**同一条件を最低2回は回して、ゆらぎの幅を測ること。** いまは 0.005 の差を
議論できる根拠がない。deck の「複数シードでの再現性確認」がここで効いてくる。

もう1つ、**モデル選択が検証の画素F値**になっている。箇所正規化損失で学習しながら、
チェックポイントは面積の指標で選んでいる。狙いと選択基準がずれている。

## 2. なぜ p=1.0 が効かなかったのか

### (a) 非単調である

広島・箇所（被覆 cov_gt=0.5, cov_pred=0.3）。

| 条件 | 箇所Recall | 箇所Precision | 箇所F |
|---|---|---|---|
| FinalFusion_SAM_APM | 0.6188 | 0.6858 | 0.6506 |
| p=0.5 | **0.6463** (+0.028) | 0.6735 | 0.6596 |
| p=1.0 | **0.5953** (−0.024) | 0.6869 | 0.6378 |

島根でも同じ形（0.4820 → 0.4879 → 0.4766）。

p=0.5 は意図どおり Recall を上げた。p=1.0 は**ベースより下**。
機構が正しく効いているなら単調に上がるはずで、そうなっていない。

### (b) 飽和した勾配を8倍しても飽和したまま

`instance_loss.py` の設計メモにある
**「被覆0.5を落ちた箇所の 69.4 % は1画素も出ていない」**——ここが効かない理由そのもの。

1画素も出ていない＝その画素のロジットが大きな負の値に張り付いている。
シグモイドの微分がほぼ0なので、**重みを8倍しても勾配は0のまま**。

重み付けが効くのは「あと少しで届く画素」に対してであって、
「完全に見えていない箇所」には届かない。そして落ちている箇所の7割はそちら。

### (c) 本命 — ボトルネックで情報が消えている

タイルの実解像度は **1画素 ≈ 4.48 m**（タイル幅 573 m / 128 px）。
`MultiEncoderUNet` は4段プーリングで、ボトルネックは 8×8 = **71.7 m/画素**。

| 箇所の大きさ | 実寸 | 128 | 64 | 32 | 16 | **8（ボトルネック）** | 実測の見逃し率 |
|---|---|---|---|---|---|---|---|
| 50 px | 32 m四方 | 7.1 | 3.5 | 1.8 | 0.9 | **0.44 px** | **90.5 %** |
| 100 px | 45 m四方 | 10.0 | 5.0 | 2.5 | 1.3 | **0.62 px** | 58.7 % |
| 300 px | 78 m四方 | 17.3 | 8.7 | 4.3 | 2.2 | **1.08 px** | 42.2 % |
| 1000 px | 142 m四方 | 31.6 | 15.8 | 7.9 | 4.0 | 1.98 px | 33.9 % |
| 3000 px | 245 m四方 | 54.8 | 27.4 | 13.7 | 6.9 | 3.42 px | 19.3 % |

見逃し率は `FinalFusion_SAM_APM` / 広島 / 被覆0.5。タイル内の平均箇所サイズで層別した。

**見逃し率が、ボトルネックでの画素数に対応している。**
そして **300px 以下はボトルネックでサブピクセル**、つまり存在しない。

損失関数は「モデルが持っている情報の使い方」を変えるもの。
**プーリングで捨てられた情報は、どんな重み付けをしても戻らない。**

p=1.0 が効かなかったのは損失の設計が悪かったからではなく、
**損失で解ける問題ではなかった**と考えている。

同時にこれは、**スキップ接続を箇所特化にする案が機構的に正しい**ことを意味する。
300px 以下の箇所がデコーダに届く経路は、スキップ接続しかない。

### 参考: 予測が1箇所も出ていないタイル

218 / 2,964 タイル（7.4 %）。そこに正解が 308 箇所ある。
そのタイルの平均箇所サイズの中央値は 124 px で、全体の 328 px より小さい。

## 3. 損失のアイデア

それでも損失でやるなら、という順。②③は①が効いてから。

### ① 箇所ごとの top-k プーリング損失（MIL 型）— 一番安い

失敗モードが「1画素も出ていない」なら、
**箇所ごとに『最低でもどこか1点は出せ』**と言うのが直接的。

```
L_det = mean_over_instances ( 1 − topk_mean_{j ∈ g_i}(pred_j) )^γ
```

- 箇所の**大きさに関係なく1項**。重み設計も `a0` も `p` も要らない。サイズ偏りが構造的に消える
- `max` だと勾配が1画素にしか流れないので `top-k`（k = min(10, |g_i|)）か logsumexp
- 既存の Focal Tversky に `λ·L_det` を足すだけ。FP側は現状どおり画素で罰するので、
  塗り広げ方向への暴走は面積側が抑える
- **「まったく出ていない箇所 26.5 %」を直接狙う唯一の項**

`make_instance_weight` の `ndimage.label` がそのまま使えるので実装は小さい。

### ② 箇所ごとに Tversky を分解して平均

いまの実装は**タイル単位の Tversky 比の中で画素を再配分**している。
分母に他の箇所も入るので、箇所ごとの正規化が厳密には効いていない。

```
cov_i = Σ_{j ∈ g_i} pred_j / |g_i|        L = mean_i (1 − cov_i)^γ
```

被覆方式の箇所Recallの素直な微分可能版。①より穏当だが、①のほうが失敗モードに直撃する。

### ③ トポロジカル損失（Betti数 / パーシステントホモロジー）

**連結成分の個数そのものを罰する**損失。
Hu et al., *Topology-Preserving Deep Image Segmentation* (NeurIPS 2019) 系。
箇所数評価と目的関数が一致するという意味では最も筋が通っている。
ただしタイルごとに persistence diagram を計算するので重く、学習も不安定になりやすい。
4節のフラクタル特徴と地続き。

### ④ 境界系（Hausdorff, Boundary DoU）は勧めない

`instance_summary.csv` を見ると、飲み込まれていない箇所の
**予測面積/正解面積の中央値は 1.00**。境界の質は問題になっていない。ここは空振りする。

## 4. カオス理論 / Takens の埋め込み定理について

**そのままでは適用できない。**

Takens の定理は「**決定論的力学系**の**スカラー時系列** x(t) から、
遅延ベクトル (x(t), x(t−τ), …) でアトラクタを微分同相に復元できる」という主張。
必要なのは**時間軸と軌道**。

静止した DEM タイルには時間も軌道もない。ラスタ走査で1次元化して遅延埋め込みすることは
計算としては可能だが、出てくる「アトラクタ」は**走査順序という人工的な順番の産物**で、
地形の力学的構造ではない。理論の保証は何も付いてこない。

### Takens が本当に使える場面

時系列があるとき。

- 多時期の衛星画像（同一地点の時間変化）
- 降雨量・地下水位・InSAR による変位の時系列

斜面の**崩壊予測**をやるならここは正攻法。
ただしいまの研究は「静的な地形から警戒区域（＝行政が指定した領域）を抽出する」タスクで、
対象が違う。

### 「フラクタルで特徴を取る」という着想自体は正しい

理論の名前を外して意図のほうを実装するなら、これらは実在する手法。

| 手法 | 中身 | 実装コスト |
|---|---|---|
| **局所フラクタル次元** | ボックスカウント法 or バリオグラム法で、窓ごとの地形の粗さのスケーリング指数。地形学で実績あり | 低。scipy で書ける |
| **ラキュナリティ** | 「隙間っぽさ」。フラクタル次元が同じでも質感を区別できる | 低 |
| **マルチフラクタルスペクトル** | スケールごとに指数が変わる度合い | 中 |
| **パーシステントホモロジー** | 標高の劣位集合のトポロジー（尾根・谷・窪地）を全スケールで記述。persistence image にすればチャネルとして入る | 中〜高 |

**パーシステントホモロジーが、この直観の数学的に筋の通った版**だと思う。
「スケールをまたいだ地形の構造」を捉えるという狙いが同じで、しかも
**連結成分を数える**という点で箇所数評価と発想が一致する。
入力特徴としても（persistence image）、損失としても（3節③）使える。

いずれも `precompute_weights` と同じ要領で事前計算してチャネルに足す形になり、
deck の「特徴量の追加」の枠にそのまま収まる。

**ただし期待値としては、5節のアーキテクチャより下。**
入力チャネルを増やしても、2節(c) のボトルネックで消える問題は残る。

## 5. スキップ接続を箇所特化、デコーダを面積に

3案のうち、**唯一、実測されている失敗モードの原因に直接対応している。**
根拠は 2節(c) の表。

### なぜ Attention では効かなかったのか

deck に「32px の段で地形量を警戒区域へ +0.25 絞り込んでいる。
それでもF値が変わらない＝ゲートが冗長」とある。

これは示唆的で、**Attention ゲートは既にある特徴を重み付けし直すだけ**だから、
と考えられる。「ここに箇所がある」という情報を**新しく作る**圧力がどこにもかかっていない。

つまり、**スキップ接続に必要なのはゲートではなく監督信号。**

### 具体案: 中心点ヒートマップによる深層監督（CenterNet 風）

```
Encoder ──┬─→ (64 の段) ──→ 小さいヘッド ──→ 中心点ヒートマップ
          │                                    ↑ ガウシアン Focal Loss
          │                                   （箇所ごとに1ピーク）
          └─→ skip ─────────────────→ Decoder ──→ マスク
                                                 ↑ Focal Tversky（面積）
```

効くと考える理由。

- **中心点は箇所の大きさに依存しない。** 50px の箇所も 3000px の箇所もピークが1つ。
  **サイズ偏りが構造的に消える** — 損失の重み付けでやろうとしたことを、
  アーキテクチャ側で、`a0` も `p` も使わずに実現できる
- **勾配が飽和しない。** 中心点という明確な正例があるので、2節(b) を回避できる
- **高解像度の段で監督するのでボトルネックを通らない。** 2節(c) を回避できる
- デコーダは Focal Tversky のまま＝**「デコーダーは面積」**

### 推論時にもう一段使える

検出した中心点の周りだけ**しきい値を下げる**（あるいは中心点から領域成長させる）。
**「まったく出ていない箇所 26.5 %」を推論側から直接回収できる。**
箇所Recall の天井 0.735 を押し上げる、ほぼ唯一の手。

### どの段に置くか

**64×64（9.0 m/画素）が候補。** 50px の箇所が 3.5 画素になるので、まだピークを立てられる。
128×128 でも良いが計算が重くなる。

### 実装

- 正解の中心点は `ndimage.center_of_mass`。`precompute_weights` と同じ要領（数分）
- `dc5lib/models.py` に新クラス、`MODEL_CLASSES` に登録
- ノートブックは出力2つ・損失2つになるので、`experiments/UNet_SAM_InstLoss/` の配線を参考に
- `L = FocalTversky(mask) + λ · GaussianFocal(heatmap)`、λ は 0.1〜1 で振る

### 発展 — スキップ接続自体に機構を入れる

上が効いたら、予測した中心点マップでスキップ特徴を変調する（掛ける / concat する）段に進む。

**ただし順番が大事で、まず深層監督だけを入れて効果を確認すること。**
監督なしで変調機構だけ足すと、Attention のときと同じ
「絞り込めているが精度に繋がらない」になる。

## 6. 優先順位 — 手つかずで残っている大きい玉

損失とアーキテクチャの前に、**もっと大きくて安い玉が2つある。**

### ① bg_ratio がいまだに全条件 0.0

```
$ grep -h bg_ratio experiments/*/config.yaml | sort | uniq -c
     20 bg_ratio: 0.0
```

deck 自身が「最優先」と書いていて、背景タイル 23,332 枚を1枚も使わず、
広島で 47.5 % のタイルに誤検出が出ている。**コードは割合指定に対応済み**なので
config を1行変えるだけ。箇所Precision を直接押し上げるはずで、
伸びしろとしては損失の小細工より大きい。

### ② 航空写真を9分の1に縮めて捨てている

`tools/dataset_build/fetch_aerial_v2.py:110`

```python
img = Image.fromarray(crop).resize((dem_size, dem_size), Image.BILINEAR)
```

ズーム18（≈0.49 m/画素）で取得した画像を **128×128（4.48 m/画素）にリサイズ**している。
573 m のタイルなら本来 **約 1165×1165 画素**の情報がある。

つまり **線形で約9倍、面積で約83倍の解像度を捨てている。**
そして捨てているのは、まさに小さい箇所を見分けるための情報。
32 m 四方の箇所は、いま 7×7 画素だが、元の解像度なら **64×64 画素**ある。

`MultiEncoderUNet` は DEM と APM が別エンコーダなので、
**APM 側だけ 512×512 で入れて途中で DEM 側に解像度を合わせる**非対称構成が自然に書ける。
タイルキャッシュが残っていればデータセット再構築だけで済む。

### インパクトの見立て

```
② 航空写真の解像度  >  ① bg_ratio  >  5節 アーキテクチャ  >  3節 損失  >  4節 特徴量
```
