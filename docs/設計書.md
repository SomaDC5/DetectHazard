## 1. この設計が生まれた理由（実測）

2026-10-29 に全条件を機械で調べたところ、こうなっていた。

| | |
|---|---|
| 条件の数 | 55本 |
| **config の `train:` が1項目も届いていなかった条件** | **30本** |
| 乱数を固定していた条件 | **12本だけ** |
| テストで最良エポックを選んでいた条件 | 3本（いま `ensemble: false`）|

原因は**既存のノートブックをコピーして条件を増やしたこと**である。
コピーの瞬間は正しくても、config を直したときノートブックは直らない。
**「config に書いてあるから効いている」が嘘になる。**

> だから設計の中心は1つだけである ──
> **値と手順をノートブックに置かない。** `config.yaml` と `dc5lib/` に置く。

## 2. 層の分け方

```
config.yaml           値だけ。手順を書かない
  ↓
dc5lib/               手順。ここだけが処理を持つ
  registry   条件を読む（Condition）
  traincfg   学習設定を読む（TrainCfg。既定値はここ）
  splits     分割を決める・指紋を出す
  pipeline   pkl → DataLoader（build_loaders）
  models     構造を組む（build_model_for）
  train      学習ループ（fit）
  ckpt       重みに素性を持たせる
  evaluate   測る（評価ロジックは持たない）
  union      和集合の定義と検査
  results    記録する
  ↓
ノートブック / tools/run_*.py     dc5lib を順に呼ぶだけ
  ↓
analysis/run_*.py     42〜45 の数字を出すスクリプト
```

### なぜ `evaluate.py` が「評価ロジックを持たない」のか

箇所評価は `analysis/instances.py` と `dc5lib/instance_eval.py` にあり、
`42`〜`45` の数字はそこで出している。
**同じ数字を2か所で出すと、いつか食い違う。** だから `evaluate` は
設定（`PRIMARY`・連結性8・最小サイズ10）を揃えて呼ぶだけにしてある。

### なぜ `fit` が早期終了まで持つのか

`FinalFusion_SAM_APM_OverlapTrain` は `early_stop_patience` が config にも
ノートブックにも無く、**検証F値が ep115 で頭打ちのまま 1000 エポック回り続けた。**
ノートブックごとに学習ループを書き写していたからである。

### なぜ学習と評価のノートブックを分けるのか

同居していたせいで、**学習側だけ config に直して評価側が直書きのまま残った**
（`設計図_現状.md` の `2.3`）。分ければ両方が `build_loaders` を通る。

## 3. 分割とデータリーク

### 分割は指紋で照合する

`dc5lib/splits.py` の `fingerprint(parts)` と `tiles_fingerprint(no)`。
**同じ指紋なら同じタイルが同じ側にある。** 和集合に混ぜる前に必ず見る。

- `fingerprint` … 分割の指紋（広島 random/42 は `653b8cbe3d28`、
  **島根は `2dd13cd65a6c`**）
- `tiles_fingerprint` … **pkl のタイルの並び**の指紋
  （広島 `a75ad23bad3e` / 島根 `ff11694a9f3f`）

並びが違えば、同じ分割指定でも別のタイルが選ばれる。だから2つある。

> **`fingerprint` は地域をまたいで比べられない**（2026-11-08 に実測で確定）。
> `fingerprint(parts)` は**タイル番号そのもの**を混ぜるので、
> 同じ `random_state` でも地域が違えば必ず違う値になる。
> **「同じ指紋なら同じ分割」は地域の中だけの判定である。**
> 実装書 `4` が「島根も同じ」と書いていたのは誤りで、直した。

**`tools/audit_splits.py` は2つの指紋を両方とも記録と照合する**
（2026-11-08）。それまでは**並びの指紋しか画面に出しておらず**、
分割の指紋は計算して捨てていた。
条件どうしのタイル集合の比較は指紋より強い検査だが、
**集合が同じなのに指紋が違えば `fingerprint()` 自体の壊れ**なので、
そこも突き合わせる。

### 近傍（オーバーラップ学習）に背景タイルを使ってよい理由

`OverlapDataset` は窓をずらして切るので、タイルの外側が要る。
そこに貼るのは `allowed_except(38148, idx_val, idx_test)` の 32,221枚。

**背景タイル（警戒区域が1画素も無い）はどの分割にも属さない**ので、
近傍に使ってもリークではない。入れると 8近傍が揃うタイルが
**0.2% → 8.7%**（平均 3.28 → 5.64 / 8）に増える。

**`allowed=None` は書かない。** 全タイルを貼るので検証・テストが漏れる。
**`OverlapDataset` が `allowed=None` を拒む**（2026-11-08。レビュー 4 で、
`build_loaders` の assert は `allowed_except` の結果をその入力と比べているだけで
**必ず通る**ことが分かった。歯止めを渡す側ではなく受ける側に置いた）。

### `ensemble: false` にする条件

| 条件 | 理由 |
|---|---|
| `FinalFusion_SAM_APM_BlockSplit` | **別の土俵**（空間ブロック分割）|
| `Train_Hiroshima_Test_Shimane_SAM_APM` | **テストで最良エポックを選んでいる** |

混ぜると和集合の意味が変わる。`union.verify` が例外で止める。

> **2026-11-08。ブロック分割は config に書かれていなかった。**
> `audit_splits` に分割の指紋を出したら、**この条件が出発点と指紋まで
> 一致していた** ── config に `split:` が無く、`resolve` が乱数に落ちていた。
> 本当の分割は CSV の 8,914 / 2,229 / 3,673 で、`31.1` の記録と一致する。
>
> **潜在的なデータリークだった。** いまの乱数テスト（正解ありの 2,964枚）のうち
> **2,158枚（72.8%）が、この条件の学習か検証に入っていた。**
> 記録には出ていない（`metrics.csv` に0行）が、`build_loaders` 経由で
> 測った瞬間に出る。**`split:` を宣言し、`registry.check()` に検査を足した。**
> ※ 2026-11-11 に `audit_splits` で測り直した。テストは 2,964枚である
> （ここに「2,963枚」と書いていた。2,963 は検証の枚数）。
>
> **宣言できない条件もある** ── `Train_Hiroshima_Test_Shimane_SAM_APM` は
> 検証を取らない 8:2 で、`resolve` は `val_size=0` を扱えない。
> ただし**テストは一致する**ので評価は正しく、架空なのは `val` だけである。

### `split:` を宣言しただけでは足りなかった — **`analysis/` の道は分割を見ない**

データを読む道は2本ある（2026-11-11 のレビュー）。

| | `dc5lib` の道 | `analysis/` の道 |
|---|---|---|
| pkl を読む | `dc5lib/data.py` | `analysis/data.py` |
| 広島のテスト | `splits.resolve`（**条件の `split:` を見る**）| `hiroshima_test_indices`（**見ない。いつも random/42**）|
| 使う側 | `tools/run_*`・雛形 | `analysis/run_*`（展望 42〜48 の数字）|

既定の乱数分割の条件については、2本は**同じ 2,964枚**を選ぶ（実測。添字の並びまで一致）。
だから既存の数字は正しい。**食い違うのは別の分割で学習した条件**で、
`FinalFusion_SAM_APM_BlockSplit` を `analysis/` の道で広島に掛けると、
**上の 2,158枚の漏れがそのまま起きる** ── `split:` を宣言しても、
こちらの道は config の `split:` を一度も読まないからである。
逆向き（乱数分割の条件をブロック分割のテスト 3,673枚に掛ける）は **2,867枚**が漏れる。

**記録には出ていない**（`metrics.csv` にブロック分割の条件の行は0行、
`hiroshima_block` の行も0行。実測）。**実害が出る前に歯止めを置いた** ──
`splits.fits_subset(cond, subset)` が「その条件をそのタイル集合で測ってよいか」を
config だけから決め、`analysis/` の入口が**推論の前に**呼ぶ（§7）。

**道を1本にまとめることはしない**（§8）。`analysis/` の道は 42〜48 の数字の
出どころで、作り直すと過去の数字と1枚でも違ったときに原因を追えない。
**まとめずに、入口で止める。**

## 4. 評価の軸 — **なぜ画素ではなく箇所か**

画素単位のF値では「**危険区域を一件見つけられたか**」が測れない。
実務は箇所で数える。だから箇所単位の評価軸を設計した。

| | 値 | なぜ |
|---|---|---|
| `PRIMARY` | `被覆 (cov_gt=0.5, cov_pred=0.3)` | 対応づけ方式を7通り実装して選んだ（`docs/箇所数評価_設計メモ.md`）|
| 連結性 | 8近傍 | |
| 最小サイズ | 10px | これ未満は数えない |

**この4つを変えると過去の数字と比べられない。** `PRIMARY` を使い回す。

### 判定の作法 — **ゆらぎ幅（帯）**

同じ設定でシードを変えて学習すると箇所F が動く。その幅を実測してある。

| | 1段目の帯 | 2段目の帯 |
|---|---:|---:|
| 広島 | **0.0071** | 0.0031（`17.2`）／和集合つき 0.0019〜0.0061 |
| 島根 | **0.0198** | 0.0018〜0.0052（`45.5`）|

**帯を下回る差は「差が無い」。** 判定は2つの見方でする。

1. **幅の比**（差 ÷ 帯）
2. **シードの範囲が重なるか**（こちらのほうが強い根拠）

**食い違ったら両方書く。** 6本の和集合は広島で幅の比 1.0帯（ふち）だが
範囲は重ならない。だから「箇所F の差は小さく、再現率と適合率の交換が本体」
と書いた（`45.5`）。

> **1段目の帯を2段目の判定に流用しない。** `16.3` でやって `17.2` で訂正した。

## 5. 和集合（アンサンブル）

### なぜ確率平均ではなく OR か

入力の異なる条件は**見逃す場所が重ならない**（0画素の見逃しの Jaccard 0.4766）。
だからマスクを OR で重ねる。**OR は `max(ロジット) > 0` と同じ**なので、
刈り取りに渡す `logit_max` が自然に定まる。

確率平均は AND 寄りで、断片化して失敗した（`Ens_OverlapPair2`）。

### **払う通貨で考える**

| | 箇所R | 箇所P |
|---|---|---|
| 和集合（本数を増やす）| **上がる** | 下がる |
| 刈り取り（2段目）| 下がる | **上がる** |
| 合意数チャネル | 下がる | **上がる** |

**和集合は適合率を払って再現率を買う**ので刈り取りと相補的である。
`20` のロジットヒンジは逆に再現率で払って適合率を買ったので**冗長だった。**

`45.7` がこの考え方の一番はっきりした例 ──
6本に増やして落ちた箇所P（−5.7帯）を、
**増やしたこと自体が生んだ情報（何本が反応したか）で取り返した**（+8.1帯）。

### **成否は床で見る。箇所F ではない**

| 見るもの | 意味 |
|---|---|
| **床** | どの構成員も1画素も光らない正解の割合。**ここが下がったかで決める** |
| 天井（1 − 床）| 構成員を増やして届きうる上限 |
| 刈り取り後の上限 箇所F | `2R/(1+R)` |
| 和集合の箇所F | **上がらないのが普通。** 価値は上限にある（`42.1`）|

**床が下がっても再現率は上がらないことがある**（`45.3`）──
下がった分の多くは「1画素は光るが覆い50%に届かない」止まりで、
**2段目を通して初めて再現率になる。**

### 構成員の宣言を1か所に集めた理由

以前は構成員の名前が3か所に別々に並んでいた
（`run_stage2_room.py` / `run_miss_overlap.py` / `audit_splits.py`）。
**どれかを足し忘れると「測った集合」と「語っている集合」が食い違う。**
いまは `unions/*.yaml` にだけ書く。

`recorded:` が付いた定義は**動かさない** ── その集合で出した数字が docs に
載っているので、構成員を変えると過去の記述が嘘になる。変えたいときは新しい yaml。

### `members` と `.all` を分けている理由（**事故の元**）

`run_union_blind.py --members` は**基準込みの全員**が要り、
`run_stage2_*.py --union-with` は**基準を含まない相方**が要る（基準は `--stage1`）。

**取り違えても値が静かに小さくなるだけで落ちない。** 実際に5本で測って
「6本」として記録した（`設計_アンサンブルの記録.md` の `4.1` の D）。
いまは `--name` の定義と `--members` が違えば**推論の前に止まる。**

## 6. 記録

### なぜ記録するのか

数字が docs と使い捨てのログにしか無いと、**測り直しても復元できない**。
`41.3` の面積層別の2行は結局再現できていない。

**数字を docs に書くなら記録する**（`CLAUDE.md`）。

### シードごとに後処理の定義を分ける理由

`record_eval` は古い記録を
`(condition, region, tileset, scope, metric_kind, setting)` で**消す**。
`model`（2段目の重み名）は鍵に入らないので、
**同じ名前で複数シードを記録すると後のものが前を消す。**

**鍵は変えない** ── 変えると過去845件の記録の同一性が変わる。
だから定義を `_s1`/`_s2`/`_s3` と分ける。
既存の `condition` 名も**改名しない**（`metrics.csv` の履歴が切れる）。

### 記録するのは**テスト**だけ

鍵に `split` が入らないので、`evaluate(..., split="val", record=True)` は
**テストの行を検証の値で置き換える**（2026-11-08。レビュー 1.1）。
`note` には split が残るが、鍵が同じなので行は1本しか残らない。

**鍵は変えない**（上と同じ理由）。だから**記録する側を止める** ──
`evaluate` は `record=True` かつ `split != "test"` なら
**推論の前に** `ValueError` で止まる。検証の値を見たいときは `record=False`。

> **同じ穴が2段目の経路に残っていた**（2026-11-12 のレビュー）。
> `analysis/run_stage2_eval.py` は `--split val` と `--record` を両方受け、
> 記録は `run_overlap_prune.record` に渡すだけで split を見ていなかった。
> しきい値を選ぶために `--split val` で回す手順なので、**`--record` を付けたまま
> 回せば、その定義のテストの行が検証の値に置き換わる。** いまは推論の前に止まる。
> 2026-11-08 に `evaluate` を塞いだとき、**記録を書く場所を数えていなかった**
> （書く場所は6つある。`docs/レビューの手引き.md` の `7.7`）。

### `tileset` のラベルは**枚数を指していない。** 表に無い枚数は記録しない

鍵に枚数も `split` も入らないので、**「どのタイルを測ったか」を言えるのは
`tileset` の4語だけ**（`警戒のみ` / `警戒+背景` / `全件` / `背景のみ`）。
ところが**同じ語が地域で違う集合を指している**（`results/metrics.csv` の実態）。

| 地域 | ラベル | 実際の枚数 | 既存の行（条件の数）|
|---|---|---:|---:|
| 広島 | `警戒のみ` | **2,964**（テスト分割）| 414（48）|
| 島根 | `警戒のみ` | **9,679**（正解ありの全件）| 17（17）|
| 島根 | `全件` | 24,569 | 420（48）|

> **訂正（2026-11-11）。** 既存の行を「47 / 17 / 45」と書いていたが、
> `metrics.csv`（1,015行）を数え直すと上のとおりで、**47 と 45 は再現できなかった**
> （何を数えた値か分からない）。本文のあちこちにある「既存47件」「45件」は
> **「その地域・そのラベルの既存の行」**と読むこと。
> `n_tiles` が入っている行はすべて表の枚数と一致する（2,964 / 9,679 / 24,569）。

> |---:|---|---|
> | 24,569（主系統）| `全件` | `analysis/run_overlap_eval.py --record` |
> | 9,679（補助 `gtonly`）| `警戒のみ` | **`templates/eval_shimane.ipynb` のセル3**（`record=True` にした）|
> | 1,936 | — | 無い（記録しない）|
>
> 補助の経路は**それまで1本も無かった** ── 9,679枚を `evaluate` に渡せるのは
> あのセルだけで、`record` を渡していなかった。**渡すようにした。**

### ずらした窓を「素のタイル」として記録しない

`build_loaders` が返す `datasets["train"]` は、オーバーラップ条件
（`overlap.max_shift > 0`）では**乱数でずらした窓**を返す。学習用だからである。
`eval_shimane.ipynb` のセル3は、補助の 9,679枚を作るのに
`train`・`val`・`test` の3つをつないでいた ── **学習の 5,807枚ぶんが
素のタイルではなかった**（2026-11-11 のレビュー。合成データで確かめた：
`max_shift=64` の学習用データセットは 200回引いて一度も素のタイルを返さない）。

- 値が**測るたびに変わる**（窓が乱数で決まる）
- `Result.describe()` は「素のタイル」と表示する
- オーバーラップ無しの条件では起きない（`max_shift=0` なら素のタイル）ので、
  **主力の条件（OverlapTrain）でだけ壊れる**

だから `build_loaders` に **`datasets["all"]`**（警戒区域ありの全件・
`deterministic=True`）を足し、セル3はそれを測る。`evaluate` は
測ろうとしている DataLoader にずらした窓のデータセットが入っていれば、
`record=True` なら**推論の前に止め**、`record=False` でも注意を出す
（歯止めは受ける側に置く。§3 の `allowed=None` と同じ作法）。

**この経路で記録された行は無い**（セル3が `record=True` になったのは
2026-11-10 で、`evaluate()` が書いた行は広島 2,964枚の4行だけ。実測）。

### 学習に使った地域では、テスト分割以外を記録しない

島根の `全件`（24,569）と `警戒のみ`（9,679）は**学習タイルを含む。**
いまは `run_training.py --region Shimane` が通る（期待値を島根にも足した）ので、
**島根で学習した重みを `eval_shimane` で測ると、学習データでの値が
「島根・警戒のみ」として残る**（4回目のレビュー A）。

重みの素性に学習した地域が入っている（`ckpt.build_meta` の `region`）。
**それを見て止める** ── 学習した地域と測る地域が同じで、
かつテスト分割でなければ記録しない。
**素性の無い古い重みでは「分からない」ので止めない**（§7 の作法）。

該当する条件は**まだ無い**（島根で学習した条件が無く、名前に Shimane を含む
`Train_Hiroshima_Test_Shimane_SAM_APM` も学習は広島）。
**実害が出る前に歯止めを置いた。**

> **歯止めが届いていない経路が3つあった**（2026-11-11 のレビュー）。
> 島根の全件を記録するのは `run_overlap_eval` だけではない ──
> `run_overlap_prune`（刈り取り）・`run_stage2_eval`（2段目）・
> `run_union_blind`（和集合）も同じ集合を記録する。5回目のレビューで
> 「`run_overlap_eval` に入っていなかった」と直したとき、**残りを数えていなかった。**
> しかも `run_overlap_eval` は推論の**あと**で呼んでいた（§7 の原則に反する）。
> いまは `evaluate.check_training_region_names(構成員, 地域)` を
> **4つとも推論の前に**呼ぶ。枚数は `regions.yaml` の `subset` から先に分かる。
> 和集合と2段目は**構成員の全員**を見る（1本でも島根で学習していれば漏れる）。

### 既定の乱数分割でなければ記録しない

広島の `警戒のみ` は「`random`/42 のテスト 2,964枚」という意味であって、
**`split["n_test"]` が何枚でも受け入れるという意味ではない。**
`FinalFusion_SAM_APM_BlockSplit` のテストは 3,673枚の**別の集合**で、
そのまま記録すると表の 2,964 と食い違う（4回目のレビュー E）。
鍵に条件名が入るので他の条件の行は消さないが、**ラベルが嘘になる。**
`_recordable` は `splits.is_standard(loaders.split)` が偽なら `{}` を返す。

### 置き換える前に古い値を見せる

`record_eval` は同じ鍵の古い JSON を消す。**消す前に古い R/P/F を出す**
（4回目のレビュー A2）。島根の補助 9,679枚は既存17件と同じ鍵になるので、
**初めて回すときに何を置き換えるのかが画面に出る。**

> **出すだけで、止めはしない。** 鍵の形は変えないと決めてあるので
> （§8）、同じ鍵の記録は上書きされる。**画面に残すことが歯止めの代わり**で、
> 消してよいかを尋ねる仕組みは無い（2026-11-10 の5回目のレビュー 3）。
> 最初の版は `unlink` の**あと**に出していたので、**順番を直した。**
>
> **同じ `eval_id` の上書きは、何も出ていなかった**（2026-11-11 のレビュー）。
> 上の表示は「鍵が同じで `eval_id` が違う」古い記録だけを見る。
> `evaluate` は `run_id` を重みの素性から作るので、**同じ重みを測り直すと
> `eval_id` まで同じになり、黙って置き換わる。** 値が同じなら問題ないが、
> 測り方を変えたとき（別の集合を同じラベルで測った、など）に気づけない。
> いまは**値か枚数が違うときだけ**旧と新を出す。

**島根のテスト 1,936枚はここで止まる。** 2026-11-08 の直しは
「全件」の行を守っただけで、**同じ衝突が「警戒のみ」の17件に移っていた。**
**これは島根に限った話ではない** ── 広島の正解ありタイル 14,816枚を
`eval_shimane` と同じ手で測って記録すれば、既存47件と同じ鍵で衝突する。
島根は `subset: all` のせいで**先に踏んだ**だけである。

**`tileset_label` は変えない** ── `run_overlap_eval.py` は本当に
全24,569枚で測っていて、そちらは「全件」で正しい。直すのは**呼ぶ側**である。

### 床と天井を列に入れない理由

箇所R/P/F の形をしていない。`recall=天井` のように入れると**列の意味が壊れる。**
`note` に件数と出どころの CSV 名を書く。
表で扱いたくなったら、そのとき別の表を設計する。

## 7. 歯止め（**止めるなら推論の前に止める**）

長い推論のあとで怒られる設計は、1時間を無駄にする。
だから検査は**データを読む前**に置く。

| 歯止め | 何を防ぐか |
|---|---|
| `run_training.py` の `EXPECT`（**広島・島根の両方**）| 分割が既存条件と違うまま学習を始める。期待値の原本は `dc5lib/splits.py` の `EXPECT` |
| `registry._check_overlap_names` | 名前が `OverlapTrain`/`OL` なのに config に `overlap` が無い（**素のタイルで学習してしまう**）|
| **`registry._check_declared_split`** | csv 分割なのに config に `split:` が無い（**乱数分割に落ちて、学習時と違う分割になる**）。判定は `registry.split_declaration` に1つだけ置く |
| `run_union_blind.guard_save` | 構成員が違うのに無印の CSV を上書きする（`44.4`/`44.6` の出どころ）|
| `run_union_blind` の `--name` 照合 | `members` と `.all` の取り違え |
| `run_stage2_eval` の `union_with` 照合 | 記録と実際に測ったものの食い違い |
| `run_stage2_*` の3入力目の検査 | 1段目に建物条件を渡す（未対応。**落ちる前に言う**）|
| `union.verify` / **`union.verify_names`** | `ensemble: false` の混入・分割の食い違い。**`run_union_blind` と `run_stage2_eval` が推論の前に `verify_names` を呼ぶ**（2026-11-11 まで、`verify` を呼ぶスクリプトは1本も無かった）|
| **`splits.fits_subset`**（`run_overlap_eval.require_fit`・`config.group_by_pkl`）| **別の分割で学習した条件を、乱数分割のテストで測る**（`analysis/` の道は `split:` を見ない。§3）|
| `tools/check.py` | 直書きの値が config と違う・nbformat・`ensemble: false` の混入・**雛形が定義していない名前を使っている** |
| **`registry._check_train_keys`** | **config の `train:` に誰も読まない鍵を書く**（打ち間違いが既定のまま学習される）|
| **`build_loaders` の入力数の検査** | 1入力の条件を通して、pkl を読んだあと最初のバッチで落ちる |
| **`fit` の既存の重み・曲線の検査** | 曲線を `"w"` で開いて**中身を消し**、1エポック目で `best_model.pth` を上書きする（`best = -1.0` から始まるため）。`overwrite=True` で明示させる |
| **`fit` の `augment` / `init_from` の検査** | **config に書いたのに届かないまま学習する。** 表示は「追加学習」と出るのに、ゼロから学習していた |
| **`fit` の補助損失の検査** | **`train.loss.aux_lambda` を書いたのに、補助損失なしで学習する**（補助ヘッドは付くが一度も学習されない）。hooks に `forward` と `loss_fn` の両方があれば通す（2026-11-12）|
| **`evaluate` の split 検査** | テストの記録を検証の値で置き換える（§6）|
| **`evaluate` の枚数の検査** | **ラベルの無い枚数で記録して、別の集合の行を置き換える**（§6）|
| **`evaluate.can_record_split`** | 長い処理の**あと**で記録できないと分かる（`pkl` を読む前・学習を始める前に返す）|
| **`evaluate.can_record`** | 同じことを **`loaders` を見て**答える。`can_record_split` は地域しか見ないので、**csv 分割の条件は通ってしまい、学習のあとの `evaluate(record=True)` で初めて止まっていた**。`run_training` と雛形は学習の前にこちらを呼ぶ |
| **`evaluate` のずらした窓の検査**（`_guard_record`）| **学習用のデータセット（乱数でずらした窓）で測った値を「素のタイル」として記録する**（§6）|
| **`evaluate.check_training_region`** | **学習に使った地域で、学習タイルを含む集合を記録する**（§6）。`evaluate` と、`analysis/` の記録の経路4つ（`check_training_region_names` 経由・**推論の前**）が呼ぶ |
| **`run_training` の先頭の `_guard_before_training`** | `augment`・`init_from`・既存の重みを、**6GB の pkl を読んだあと**で止める（規則を写さず、`fit` と同じ関数を先に呼ぶ）|
| **`run_stage2_train.guard_existing_weights`** | **既存の2段目の重みを黙って作り直す。** `--name` の既定は実在する重みの名前で、後処理の定義が指している（2026-11-12）|
| **`run_stage2_eval.guard_record_split`** | `--split val --record` がテストの行を検証の値で置き換える（`evaluate` と同じ穴がこちらに残っていた）|
| **`run_stage2_eval.guard_stage2_weights`** | 別の1段目・別の相方で学習した2段目を当てる（落ちずに無意味な値が出る）。重みに書いていなければ「分からない」ので止めない |
| **`run_union_blind.guard_overwrite`** | 印つきの和集合の表（`44.7`／`44.8` の出どころ）を、別の構成員で上書きする。`guard_save` は無印の1枚しか守っていなかった |
| **`config.group_by_pkl` の3入力目の検査** | 素のタイルの集計が、建物・地質の条件で pkl を読んだあとに落ち、**既定の全条件の実行が途中で止まる** |
| **`new_experiment.condition_templates`** | 新しい条件に、条件に属さない雛形（`union.ipynb`）まで複製する |
| **`tools/test_guards.py` の写しの照合** | `analysis/` にある主系統のしきい値の写し（`COV_GT` など9本）が、原本と違う値のまま残る |
| **`audit_splits` の終了コード** | 分割が食い違っても・pkl が無くて確かめられなくても、**0 で終わって気づかない** |
| **`verify_docs.doc_claims`** | **実装書の本文が古いまま通る**（以前は本文を読んでいなかった）|
| **`splits.compare_expected`** | 分割の照合を各所で書き写して、`EXPECT` が増えたときに `KeyError` で死ぬ |
| **`tools/check_bands.py`** | **ゆらぎ幅の写しが増える**（測り直したときに古い帯のまま判定が反転する）。`check.py` から回る |
| **`tools/test_guards.py`** | **歯止めが効かなくなったことに気づかない**（`check.py` から回る。pkl も重みも読まない）|

### 分割の期待値を1か所に集めた理由

`run_training.py` の `EXPECT`・`audit_splits.py` の `EXPECT`・
`templates/train.ipynb` の照合セル・実装書 `4` の表に、
**同じ値が別々に並んでいた**（2026-11-10 の再レビュー 3）。
**構成員の名前が3か所に並んでいたのと同じ形**である（§5）。
実際に実装書の島根の指紋が間違っていて、**食い違いかけていた。**

だから原本を **`dc5lib/splits.py` の `EXPECT`** に1つ置き、
3つのコードはそこから読む（`splits.expected(region)`）。
実装書との照合は `tools/verify_docs.py` の `claims()` に足した。

**ノートブックに値を書かない**（CLAUDE.md の 1）。
`templates/train.ipynb` も `splits.expected(REGION)` を呼ぶ。
**既存の `experiments/*/train.ipynb` は触らない** ──
あれは「何を回したか」の記録なので、書き換えると履歴が変わる。

### 歯止めは**機械で確かめる**

この表は長らく「そう書いてある」だけだった。2026-11-08 のレビューで、
**「止める」と書いてあるのに通る箇所が2つ**見つかった
（`build_loaders` の assert は必ず通る・`run_training` の `EXPECT` が広島だけ）。

だから `tools/test_guards.py` を置き、`tools/check.py` から回す。
**歯止めを足したらそこに1行足す。** pkl も重みも読まないので速い。

### 「分からない」と言う

`union.verify` は素性の無い古い重みでは分割を確かめられない。
そのとき**「大丈夫」と言わず「分からない」と言って** `audit_splits.py` を促す。
**でっち上げない。**

## 8. やらないと決めたこと

| | 理由 |
|---|---|
| `record_eval` の鍵を変えない | 過去845件の記録の同一性が変わる |
| 既存の `condition` 名を改名しない | `metrics.csv` の履歴が切れる |
| 床・天井を `recall`/`precision` 列に入れない | 列の意味が壊れる |
| `ensembles.yaml` を分割しない | 旧側と同居して紛らわしいが、記録済みの定義を動かす危険が大きい |
| 既存の重みと曲線を作り直さない | 失った3本（FCN/PSPNet/DeepLabV3）の曲線も再学習しない |
| 旧側（`ensembles.yaml` / `dc5lib/ensembles.py`）を触らない | 確率平均の系統。新側（`unions/` / `dc5lib/union.py`）と別物 |
| config の `ensemble:` キーを改名しない | 53本の config にある |
| `bg_ratio > 0` を `build_loaders` で扱わない | `NotImplementedError` で止める。旧プロトコルの条件だけが使う |
| 1段目の3入力目（建物）を stage2 の経路で扱わない | 使う予定が無い。**歯止めで止める**ほうが安い |
| 補助損失（深層監督）を `fit` に実装しない | 使うのは v1／v2 の12条件だけで、段の選び方と重みの割り方が構造ごとに違う（1段・複数段・ブランチ別）。**「書いたのに届かない」ので止める。** 回すときは hooks で渡す |
| `dc5lib/models.py` の既存のクラスを直さない | 重みを `strict=True` で読むので、層の名前と順序が契約である。44本が読めることを測った。読みにくい箇所（同じ値を返す条件分岐・1行に潰れた `assert`）も**そのままにしてある** |
| `augment` / `train.init_from` を実装しない | `augment: true` は v1 の3本、`init_from` は1本だけが使う。**どちらも「書いたのに届かない」ので止める。** 実装すると旧条件の学習が再現しなくなる |
| `record_eval` に `split` を足さない | 鍵が変わる（上と同じ）。記録する側を test に絞るほうが安い |
| データを読む道（`dc5lib` と `analysis/`）を1本にまとめない | `analysis/` の道は 42〜48 の数字の出どころ。作り直して1枚でも違うと原因を追えない。**入口で止める**（`fits_subset`。§3）|
| 1入力の条件を `build_loaders` で扱わない | 該当は `UNet_SAM_InstLoss` の1本（v1）。`OverlapDataset` は航空写真を必ず読む。**pkl を読む前に止める** |
| 旧側の記録の経路（`run_ensemble_eval.py`）に新しい歯止めを足さない | 旧側は触らないと決めてある。**学習した地域の検査も分割の検査も入っていない**ことは知っておく |
| 主系統のしきい値の写し（`analysis/` の9本）を原本読みに直さない | 帯の写しと同じ判断。値は正しく、読んでいないスクリプトを触るほうが危ない。**食い違ったら落ちる検査を置いた** |
| オーバーラップ推論の9窓を混ぜる処理（5か所の写し）を1つにまとめない | 42〜48 の数字の出どころ。3つは数値で一致を確かめた（実装書 `7.4`）。**直すときは5か所とも直す** |
| 広島の箇所F の帯（0.0071）を 0.0070 に直さない | 丸めずに引くと 0.007026 で、原本は両端を丸めてから引いた値（実装書 `5`）。直すと過去の「何帯」と合わなくなる。**ふちの判定では両方で見る** |
| 素のタイルの集計（`run_inference` ほか）に、土地利用以外の3入力目を通さない | 地質の条件（v1）が学習時に3入力目をどう正規化したかを確かめていない（未検査）。**通さずに、先に外す。** 建物の条件は `tools/run_eval.py` で測れる |
| `inputs.model_args` の「最大値が 1.5 を超えたら 255 で割る」を直さない | 航空写真の最大値が 1 以下のタイルは広島 38,148枚・島根 24,569枚に**1枚も無い**（実測）ので、外れる束は無い |
| 継ぎ足した和集合の表の `cov_union`・`n_light` を作り直さない | 読んでいるスクリプトが無い（床は `cov_<略称>` から出す）。**もとの構成員のままであること**を実装書 `7.1` に書いた |
| `reset_condition.py` で `results/evals/` を消さない | 記録は git に載る成果物。**残っている件数を出す**だけにした |
| `train:` の記述だけの鍵（`augment_params` `model_selection` `split`）を消さない | 53本の config にある当時の記録。**読まれないことを実装書 §2 に書き、増えないことを検査で守る** |

## 9. 変更の進め方
