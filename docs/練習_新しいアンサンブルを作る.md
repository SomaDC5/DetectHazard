# 練習：新しいアンサンブルを自分の手で作る

複数の学習済み条件の**予測確率を混ぜて**精度を上げる。学習は要らない。

`docs/練習_新しい条件を作る.md` がモデルを1つ増やす手順。こちらはアンサンブル版。

> **なぜ `experiments/` に置かないのか**
>
> `experiments/<条件>/` は「**1回の学習**」の単位。アンサンブルには学習が無いので、
> 置くと嘘を3つ書くことになる。
>
> | 要求 | アンサンブルの実態 |
> |---|---|
> | ノートブックが存在すること（`status` に関係なく必須） | 学習ループが無いので中身が空になる |
> | `arch` が `MODEL_CLASSES` にあること | 単一のモデルクラスが存在しない |
> | `inputs` の数が `arch.forward` と一致すること | メンバーごとに入力が違う |
>
> `registry` では永久に「重み無し」と表示され、`results/runs/` も作れない。
> そこで `regions.yaml` と同じ発想で、リポジトリ直下の `ensembles.yaml` に集める。

## 1. 混ぜる条件を選ぶ

**ここが成否を決める。** 適当に選ぶと効かない。選び方の根拠は
`docs/アンサンブルで解けるか.md` の 8〜10節にある実測。

### 1.1 絶対条件：`bg_ratio` が揃っていること

ノートブックは**背景タイルを混ぜたあとで**分割する。`bg_ratio` が違うと
`train_test_split` の結果が変わり、**テスト集合が別物になる**。

```bash
python -m dc5lib.registry   # bg_ratio 列を見る
```

混ぜると `check.py` が止める。これは実際に踏む罠。

```
アンサンブル 'Ens_X': members の bg_ratio が揃っていません [0.0, 0.1]。
分割が変わるのでタイルが突き合いません
```

### 1.2 入力を変えたほうが、構造を変えるより効く

条件間の「間違え方の違い」を Spearman 相関で測った結果（広島2,964枚、153ペア）。

| | 相関 |
|---|---|
| 中央値 | 0.795 |
| **最も低い組** | **0.596〜0.615（DEM のみ ↔ SAM+APM 系）** |
| 最も高い組 | 0.881 |

**相関が低い = 間違え方が違う = 混ぜる価値がある。** 最も低いのは入力の違いだった。

実測でも、同じ4条件なら入力を混ぜたほうが上。

| | 広島 面積F | 広島 箇所F |
|---|---|---|
| 構造4種（入力は SAM+APM 固定） | 0.6927 | 0.6732 |
| **入力2種 × 構造2種** | **0.7200** | **0.6844** |

### 1.3 条件数は、何を上げたいかで変える

| 目的 | 条件数 | 根拠 |
|---|---|---|
| 広島の面積F | **4** | 14条件にすると 0.7200 → 0.7142 に下がる |
| 広島の箇所F | **14** | 0.6844 → 0.6958 |
| **島根（汎化）** | **多いほうがよい** | 面積Fも箇所Fも14条件が最良 |

数を増やすと保守的になり、**箇所Precision を買って箇所Recall を失う**。
広島だけ見ると「増やすと面積Fが落ちる」が、島根では逆になる。

### 1.4 弱いメンバーを混ぜない

平均は弱いほうに引っ張られる。目安として**全体F1 0.67 以上**で選ぶ。

```bash
# 条件ごとの全体F1（キャッシュから。推論済みのものだけ）
python - <<'PY'
import pandas as pd
from dc5lib.paths import cache_dir
from dc5lib.registry import get
T = cache_dir("analysis", "tiles")
rows = []
for f in sorted(T.glob("*__hiroshima.csv")):
    if f.name.startswith("._"): continue
    n = f.name.replace("__hiroshima.csv", "")
    d = pd.read_csv(f)
    rows.append((2*d.tp.sum()/(2*d.tp.sum()+d.fp.sum()+d.fn.sum()), n, get(n).bg_ratio))
for f1, n, bg in sorted(rows, reverse=True):
    print(f"  {f1:.4f}  bg={bg}  {n}")
PY
```

キャッシュが無い条件は先に推論しておく。

```bash
python analysis/run_inference.py --region hiroshima
```

## 2. `ensembles.yaml` に足す

```yaml
ensembles:

  Ens_MyMix:                              # 名前。実験条件と重複させない
    label: アンサンブル 私の組み合わせ      # 図表に出る。重複すると検査で止まる
    note: >
      なぜこの組み合わせか。相関や根拠を書く。
      あとから読む自分のために、効かなかった場合もここに追記する
    members:                              # bg_ratio を揃える
      - DataOgument_FinalFusion_DEM_APM
      - AttentionUNet_SAM_APM
    weights: null                         # null で単純平均
    rule: mean                            # mean / max / median
    threshold: 0.5
    status: active                        # excluded なら一覧に出るが評価しない
```

| 項目 | 意味 | 変えると |
|---|---|---|
| `members` | 混ぜる条件名 | **`bg_ratio` が揃っていないと `check.py` が落ちる** |
| `weights` | `members` と同じ順。合計1でなくてよい | 強いメンバーを重くできる |
| `rule` | 統合規則 | **`mean` から変えないほうがよい（下記）** |
| `threshold` | 二値化しきい値 | アンサンブルでは効く可能性がある（下記） |
| `status` | `active` / `excluded` | `excluded` は候補を書き置くのに使う |

### `rule` を変えるときの注意

同じ9窓の予測で統合規則だけ変えた実測（`docs/アンサンブルで解けるか.md` 2.1）。

| 規則 | 箇所F |
|---|---|
| 中心重みつき平均 | 0.7446 |
| 単純平均 | 0.7102 |
| **最大** | **0.6974（最下位）** |

**`max` は OR の連続版で、弱いメンバーの誤検出をそのまま拾う。** 既定の `mean` が無難。

`median` は外れたメンバー1つに引きずられにくいが、**全メンバーの確率を同時に
メモリに持つ**（島根24,569枚だと1条件 805MB）。`mean` と `max` は逐次に足し込む。

### `threshold` について

**単体のモデルは出力が飽和していて、しきい値がほぼ効かない。**

| しきい値 | 箇所Recall |
|---|---|
| 0.02 | 0.6295 |
| 0.50 | 0.6191 |
| 0.98 | 0.6063 |

確率が 0.02 未満に 90.7 %、0.98 以上に 8.7 % 集まっていて、
その間（しきい値で動かせる範囲）が 0.64 % しかない。

**ただし平均すると中間値が増えるので、アンサンブルでは効く可能性がある。** 未測定。
`--prob-thr` で振れる。

## 3. 検査する

```bash
python -m dc5lib.ensembles      # 一覧 + 検査
python tools/check.py           # コミット前の全体検査
```

止まるのは次の場合。

| 検査 | 意味 |
|---|---|
| `members に無い条件があります` | 綴り間違い、または `experiments/` に無い |
| `members の bg_ratio が揃っていません` | 分割が別物になる（1.1） |
| `members に重複があります` | 同じ条件を2回書いている |
| `weights の数が members と合いません` | 順番と個数を合わせる |
| `weights に負の値があります` | — |
| `未知の rule` | `mean` / `max` / `median` のどれか |
| `threshold が 0〜1 の外です` | — |
| `同名の実験条件があります` | `metrics.csv` で区別できなくなる |
| `表示ラベルが重複しています` | 図表でどちらか分からなくなる |
| `使えるメンバーが 1 件しかありません` | 1つではアンサンブルにならない |

## 4. 測る

```bash
# まず広島で。--each でメンバー単体の値も並べて出す
python analysis/run_ensemble_eval.py --ensemble Ens_MyMix --region hiroshima --each
```

```
                             対象    面積F    面積R    面積P    箇所F    箇所R    箇所P
  DataOgument_FinalFusion_DEM_APM  0.6996  0.7027  0.6965  0.6442  0.6497  0.6388
            AttentionUNet_SAM_APM  0.6763  0.7286  0.6310  0.6542  0.6499  0.6586
         アンサンブル 私の組み合わせ  0.7052  0.7123  0.6982  0.6533  0.6529  0.6537
```

（上は 2節の `Ens_MyMix` の例そのままを実測した値。面積Fは最良単体 0.6996 を
+0.0056 上回るが、箇所Fは 0.6542 → 0.6533 でわずかに下がる。
**2条件では足りない。** 条件数の目安は 1.3）

**単体の値が `metrics.csv` と一致するかを必ず確認する。** ずれていたら
突き合わせか pkl の指定が間違っている。

メモリに注意。`systemd-run` で上限を付けると、超えてもそのプロセスだけが死ぬ。
**上限を高くしすぎるとシステム全体の OOM になってデスクトップ側が巻き込まれる**
（31GB のマシンで 22GB を許して実際に起きた）。16〜18GB が安全。

```bash
systemd-run --user --scope -q -p MemoryMax=18G -p MemorySwapMax=0 \
  python analysis/run_ensemble_eval.py --ensemble Ens_MyMix --region hiroshima
```

## 6. 記録する

`--record` を付けると `results/evals/` に入り、**`metrics.csv` に単一条件と
並んで載る**（`build_metrics_csv` は `evals/` だけを読み、`runs/` と結合していない）。

```bash
python analysis/run_ensemble_eval.py --ensemble Ens_MyMix --region hiroshima --record
python analysis/run_ensemble_eval.py --ensemble Ens_MyMix --region shimane   --record
```

1回につき9件（面積の通常・境界、箇所の全7設定）が記録される。

```bash
python tools/check.py        # metrics.csv が evals と合っているか
```

確認。

```bash
python - <<'PY'
import pandas as pd
m = pd.read_csv("results/metrics.csv")
k = m[(m.condition.str.startswith("Ens_")) & (m.metric_kind == "面積") & (m.scope == "通常")]
print(k.pivot_table(index="condition", columns=["region", "tileset"], values="f1").round(4))
PY
```

## つまずきやすいところ

| 症状 | 原因と対処 |
|---|---|
| `members の bg_ratio が揃っていません` | `bg10` 系と `bg_ratio=0` を混ぜている。どちらかに揃える |
| `pkl 間でタイル集合が違います` | 同上。`check.py` を先に通していれば起きない |
| `pkl 間で正解マスクが一致しません` | pkl のタイル順が想定と違う。突き合わせを疑う |
| 単体の値が `metrics.csv` と合わない | しきい値が違う（`--prob-thr`）か、地域の指定違い |
| OOM で落ちる | `median` を使っている、または条件数が多い。`mean` にする |
| **デスクトップごと落ちる** | `MemoryMax` が高すぎる。16〜18GB にする |
| 混ぜても単体より悪い | 弱いメンバーが入っている（1.4）。`--each` で確認 |
| 広島で良いが島根で悪い | 条件数が足りない（1.3）。増やす |

## 付録：いま定義されているもの

| 名前 | 構成 | 広島 面積F | 広島 箇所F |
|---|---|---|---|
| `Ens_Struct4` | 構造4種（入力固定） | 0.6927 | 0.6732 |
| `Ens_InputPair2` | DEM系 + SAM系 | 0.7052 | 0.6542 |
| `Ens_InputDiverse4` | 入力2種 × 構造2種 | **0.7200** | 0.6844 |
| `Ens_AllStrong14` | 全体F1 0.67以上の全条件 | 0.7142 | **0.6958** |

出発点（`FinalFusion_SAM_APM`）は 面積F 0.6727 / 箇所F 0.6513。
**学習なしで 面積F +0.047 / 箇所F +0.045** まで来ている。
これは構造を変える施策（4つ連続で ±0.005）より一桁大きい。

詳しい実測と、そこから分かったことは `docs/アンサンブルで解けるか.md` の 8〜10節。
