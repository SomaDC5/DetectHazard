## 0. 先に知っておくこと

### 0-1. この研究は何をしているか

**急傾斜地崩壊危険区域**は、「崖崩れが起きたら家に被害が出る」と行政が指定した
場所のこと。いまは人が航空写真と地形図を見ながら手作業で線を引いている。

これを **AI に自動で塗らせたい**、というのがこの研究。

入力は「その土地の形（標高・傾斜）」と「航空写真」。
出力は「ここが危険区域」という塗り絵。
正解は、行政がすでに指定している区域の図形。

```
入力                      AI                 出力              正解
┌────────┐                              ┌────────┐      ┌────────┐
│傾斜の図 │ ──┐                          │  ▓▓    │      │  ██    │
└────────┘    ├─→ [ U-Net ] ──→         │ ▓▓▓▓   │  ←→  │ ████   │
┌────────┐    │                          │  ▓▓    │      │  ██    │
│航空写真 │ ──┘                          └────────┘      └────────┘
└────────┘                                  これを正解に近づける
```

### 0-2. タイルとは

県全体を一度に処理はできないので、**128×128 画素の正方形**に切り分ける。
これ1枚を **タイル** と呼ぶ。

- 1画素 = **4.48 m** 四方
- 1タイル = **573 m** 四方（128 × 4.48 = 573）
- 広島県ぜんぶで **38,148枚**、島根県で **24,569枚**

この「タイルに切る」という決め方が、実は後半の主役になる。

### 0-3. 精度の測り方（Recall / Precision / F値）

AI が塗った場所と、正解の場所を比べる。

|  | 正解でもある | 正解ではない |
|---|---|---|
| **AI が塗った** | TP（当たり） | FP（**誤検出**） |
| **AI が塗らなかった** | FN（**見逃し**） | TN |

- **Recall（再現率）** = 正解のうち、何割を見つけられたか = TP / (TP + FN)
  → 「見逃しの少なさ」
- **Precision（適合率）** = 塗ったところのうち、何割が当たりか = TP / (TP + FP)
  → 「誤検出の少なさ」
- **F値** = Recall と Precision の調和平均。両方そこそこ高くないと上がらない

> **なぜ両方いるか。** 県全体を真っ黒に塗れば Recall は 1.0 になるが、
> Precision はほぼ 0 になる。逆に自信のある1画素だけ塗れば Precision は 1.0 だが
> Recall はほぼ 0。片方だけ見ていると簡単にごまかせるので、F値で両方を見る。

このスライドでは F値 **0.67 前後**が出てくる。だいたい3分の2あたり。

### 0-4. U-Net とは

画像を塗り分ける AI の定番の形。アルファベットの U に似ているのでこの名前。

```
大きい ┌─────────────────────────────┐ 大きい
128×128│ ──── 横流し（スキップ接続）───→ │128×128  → 出力
  64×64│  ──── 横流し ─────────────→  │64×64
  32×32│   ──── 横流し ───────────→   │32×32
  16×16│    ──── 横流し ─────────→    │16×16
   8×8 └──── ボトルネック ────────────┘
        縮めていく          戻していく
        （エンコーダ）      （デコーダ）
```

- **縮めていく（エンコーダ）**: 画像を半分ずつ小さくしながら特徴を取る。
  小さくするほど「広い範囲を一度に見られる」が、「どこにあるか」は粗くなる
- **ボトルネック**: いちばん縮んだところ（8×8）
- **戻していく（デコーダ）**: また倍々に広げながら塗り絵を作る
- **スキップ接続（横流し）**: 縮める途中の各段を、戻すときの同じ大きさの段に
  そのまま渡す。これが無いと、戻すときに位置が粗いままになる

> **たとえ。** 地図を縮小コピーしていくと、「ここは山、ここは街」という
> 大まかな話は分かるが、家1軒の位置は分からなくなる。
> スキップ接続は、縮小前のコピーを手元に残しておいて、
> 清書するときに見比べられるようにする仕組み。

本研究は入力が2種類（地形量と航空写真）なので、**エンコーダを2本**持つ。
どこで合流させるかで Early / Middle / Final と呼び分ける。

### 0-5. 学習まわりの言葉

| 言葉 | 意味 |
|---|---|
| **パラメータ** | AI の中にある調整つまみの数。43.58M なら4358万個 |
| **エポック** | 訓練データを1周すること。1000エポック＝1000周 |
| **損失関数** | 「どれだけ間違っているか」を1つの数字にしたもの。これを下げる |
| **勾配** | つまみをどっちに回せば損失が下がるかの向き。これが0だと学習が進まない |
| **過学習** | 訓練データを暗記してしまい、初めて見るデータで当たらなくなること |
| **汎化** | 初めて見るデータでも当たること。過学習の反対 |
| **訓練/検証/テスト** | データを3つに分ける。訓練で学び、検証で止めどきを決め、テストで最終評価 |

## 第1章：評価のしかたを作った（スライド5〜8）

### スライド5 ― 章の導入

これまでは **面積（画素数）** で測っていた。
「正解の画素のうち何割を塗れたか」という測り方。

でも行政が扱う単位は **「何箇所」**。
「崖崩れ危険箇所が3箇所ある」という数え方をする。

そこで **箇所数で数える評価** を設計した。

### スライド6 ― 面積評価だけでは足りない

箇所で数えるには、「AI の塗った領域」と「正解の領域」を1対1で
対応づける必要がある。物体検出でよく使うのが **IoU** という尺度。

**IoU = 重なった面積 ÷ 合わせた面積**

```
   正解 ███         AI ▓▓▓
        ███            ▓▓▓

   ぴったり重なる → IoU = 1.0
   半分だけ重なる → IoU = 0.33
   全く重ならない → IoU = 0
```

ふつうは「IoU が 0.3 を超えたら当たり」と決める。
ところが、この課題では2つの落とし穴があった。

#### 落とし穴① 飲み込み

近くに正解が3つ並んでいるとき、AI が大きく1つに塗ってしまうことがある。

```
正解:   ██    ██    ██        ← 3箇所
AI:     ▓▓▓▓▓▓▓▓▓▓▓▓▓▓        ← 1つの大きな塗り

1対1で対応づけると… 1個だけ当たり、残り2個は「見逃し」扱い
```

実測すると、

- **2個以上を覆ってしまった予測**: 833個
- **飲み込まれた正解**: 1,803個（全体の **20.1%**）
- **1つの予測が覆った最大数**: 8個

**正解の5分の1が、この数え方のせいで不当に見逃し扱いになっていた。**

#### 落とし穴② 小さい箇所では IoU が構造的に上がらない

正解が小さいと、少しずれただけで IoU が急落する。

- 100px 未満の正解が **1,984個（22%）**
- そこでの最良 IoU の平均は **0.159** しかない（全体平均は 0.388）
- つまり **しきい値 0.3 を最初から超えられない**

#### 決め手になった数字

> 飲み込まれた正解は、実際には予測にほぼ覆われている
> （**被覆 0.5 以上を 89.9% が通過**）のに、
> **IoU では 37.7% しか通らない。**

同じ現象を見ているのに、測り方で 90% と 38% に割れる。
これは測り方のほうが間違っている、という判断になる。

### スライド7 ― 採用した評価「被覆方式」

IoU をやめて、**「覆われているか」だけを見る**方式にした。

| 判定 | 条件 |
|---|---|
| 正解を**検出できた** | 正解の **50%以上**が予測に覆われている |
| 予測が**的中した** | 予測の **30%以上**が正解に当たっている |

**1対1に縛らない**のがポイント。1つの大きな予測が3箇所を覆っていたら、
3箇所すべて「検出できた」と数える。これで飲み込み問題が消える。

- **箇所Recall** = 検出できた正解 ÷ 正解の総数
- **箇所Precision** = 的中した予測 ÷ 予測の総数

#### 方式を変えるとどれだけ動くか

| 方式 | 箇所Recall | 箇所Precision | 箇所F値 |
|---|---|---|---|
| **被覆（0.5 / 0.3）← 採用** | 0.6188 | 0.6858 | **0.6506** |
| 被覆（0.3 / 0.3） | 0.6632 | 0.6858 | 0.6743 |
| IoU 多対1（0.3） | 0.5068 | 0.5617 | 0.5329 |
| IoU 厳密1対1（0.3） | 0.4998 | 0.5590 | 0.5277 |

**まったく同じ予測なのに、0.53 から 0.67 まで動く。**

> だから「どの方式で測った値か」を書かずに精度を比べることはできない。
> 以降の箇所F はすべて被覆（0.5 / 0.3）で統一している。

#### 固定したしきい値

| パラメータ | 値 | なぜ |
|---|---|---|
| 連結性 | 8近傍 | 4近傍でも 0.6504 対 0.6506 で**ほぼ動かない**ので安心 |
| **最小サイズ** | **10px** | 100px にすると 0.6506 → **0.6996** と**大きく動く**ので固定 |

**最小サイズとは何か。** くっついている画素をひとまとまり（かたまり）と
数えるとき、「10画素より小さいかたまりは最初から無かったことにする」ルール。
10画素 ≒ 200 m²（14 m 四方くらい）。点々のノイズを箇所として数えないための線引き。

**なぜわざわざ書いたか。** ここを 100px にすれば F値が +0.049 上がってしまう。
小さくて当てにくいかたまりを除外すれば成績が良く見えるのは当たり前で、
**テストの平均点を上げたいから「10点未満の答案は集計しない」と決めるのと同じ**。
だから先に 10px と決めて以後動かさない、と宣言している。

### スライド8 ― 評価の軸を4つに整理

| # | 軸 | 内容 |
|---|---|---|
| 1 | **面積評価** | 画素単位。従来からの指標 |
| 2 | **箇所数評価** | かたまり単位。行政の単位に近い |
| 3 | **境界評価** | タイル中央 96×96 だけで測る。外周の切れ端を除く |
| 4 | **オーバーラップ推論** | 窓をずらして9回推論して統合する |

①②は **「何を数えるか」**、③④は **「どこを・どう推論するか」**。

④だけは性質が違う。**学習をやり直さなくていい。**
すでにある重みに後から掛けられる。

> そしてこの④が、結果的に**唯一はっきり効いた施策**になる（第5章）。
> 第1章の時点で仕込まれている伏線。

## 第2章：既存モデルを横に並べて比べた（スライド9〜12）

### スライド9 ― 章の導入

6つの構造 × 2つの入力の組み合わせを、**まったく同じ条件で**学習した。

- パラメータの幅: 31M〜94M（3倍の開き）
- 広島 面積F の幅: 0.636〜0.699
- 最良と最悪の差: **0.063**

### スライド10 ― ベースになる構造（2枝 U-Net / Final 融合）

```
 傾斜量                          航空写真
128×128 64ch                 128×128 64ch
   ↓ 半分に                      ↓
 64×64 128ch  ← skip2（赤）    64×64 128ch
   ↓                             ↓
 32×32 256ch                   32×32 256ch
   ↓                             ↓
 16×16 512ch                   16×16 512ch
   ↓                             ↓
   └────── 連結 ──→ ボトルネック 8×8 1024ch
                          ↓
                      戻していく（デコーダ）
                      各段でスキップを連結
                          ↓
                    出力 128×128 1ch
```

- 傾斜量と航空写真を **別々のエンコーダ**で処理する
- **いちばん奥（ボトルネック）で初めて合流**させる → だから「Final 融合」
- スキップ接続は、両方の枝を連結してデコーダに渡す

**この構造が出発点。**
`FinalFusion_SAM_APM`（43.58M・面積F **0.6727** / 箇所F **0.6506**）。
以降の比較はすべてこれが基準になる。

赤で示した **skip2（64×64）** が、第3章でいじる場所。

### スライド11 ― 既存6構造の比較

#### 分かったこと① 融合の位置だけが効いた

| 融合位置 | 面積F |
|---|---|
| **Early**（入口で合流） | −0.036 と明確に悪い |
| Middle / Final / Attention / TransUNet | 0.672〜0.676 に固まる |

**入口でいきなり足すのはダメ。それ以降はどこでも同じ。**

> 傾斜の数字と写真の色は性質が違うので、
> 生のまま足し算すると混ざって情報が壊れる、と解釈できる。

#### 分かったこと② 注意機構も Transformer もパラメータ量も効かない

**Attention U-Net** とは。スキップ接続に「蛇口」を付けたもの。

```
デコーダ側の信号 ─┐
                  ├→ 足す → 1×1 Conv → sigmoid → 係数 ψ（0〜1）
スキップ ─────────┘                                  │
                                                      ↓
                                  デコーダへ ← スキップ × ψ
```

横流しする情報を、画素ごとに 0〜1 を掛けて「ここは強く、ここは弱く」と
絞ってから渡す。本研究では 4段 × 2枝 = **16個**のゲートが入っている。

結果が面白い。

| | 注意係数 |
|---|---|
| 正解の中 | 0.705 |
| 正解の外 | 0.453 |

**ゲートはちゃんと働いている。** 警戒区域の上では強く、外では弱い。
なのに F値は変わらない。

> つまり **「効いていない」のではなく「冗長」**。
> デコーダはゲートが無くても同じ答えに辿り着いていた。
> この観察が、第3章の「監督Attention」の動機になる。

**TransUNet** とは。ボトルネック（8×8）に **Transformer** を入れたもの。
8×8 = 64マスを「64個の単語」とみなし、全マス同士を総当たりで見比べさせる
（自己注意）。CNN は 3×3 の窓しか見ないので遠くの情報は何段も重ねないと
届かないが、Transformer は一発で全体を見比べられる。

**94M パラメータ（Final の2.2倍）あって、結果は 0.6728。Final と同じ。**

> なぜ効かないか。**8×8 の時点で 1画素が 71.7 m ある。**
> 警戒区域1箇所の典型サイズが 81 m 四方なので、**もう1画素分しか残っていない。**
> 地図を縮小しすぎて家1軒が点になってから「全体を見比べよう」と言っている状態。
> この気づきが、スライド17の ASPP につながる。

#### この章の一番大事な一文

> 既存4構造は **0.672〜0.681 の帯**に収まる。
> **この帯の幅が、以降「効いた」と言えるかどうかの基準になる。**

これは研究の作法として重要。
「0.005 上がりました」と言っても、もともと 0.009 の幅でばらつくなら
**意味のある差ではない。** 基準線を先に引いておくことで、
後の結果を正直に判定できるようにしている。

### スライド12 ― データ拡張だけが過学習を解いた

**データ拡張**とは、画像を左右反転・回転・少しずらすなどして、
1枚のデータを水増しすること。同じものを違う見え方で見せることで、
暗記ではなく本質を学ばせる狙い。

| | 最良エポックの位置 | 訓練F1 − 検証F1 | 最良 検証F1 |
|---|---|---|---|
| 拡張なし（15条件） | 全体の **2.6〜7.3%** | **0.33〜0.39** | 0.62〜0.69 |
| 拡張あり（3条件） | 全体の **69〜90%** | **0.098〜0.101** | 0.691〜0.695 |

読み方。

- **拡張なし**: 学習の最初の数%で検証F1 がピークに達し、あとは
  訓練F1 だけが伸びていく。訓練と検証の差 0.33〜0.39 は、**ほぼ暗記**
- **拡張あり**: 最後のほうまで検証F1 が伸び続ける。差も 0.10 程度

> **1000エポック回していたのに、良かったのは最初の 30〜70 エポックだった。**
> これはスライド34の「早期終了を入れた」につながる。

#### ところが

| | 面積F |
|---|---|
| 広島 | 0.6727 → **0.6974**（+0.025） |
| 島根 | 0.5381 → **0.5409**（+0.003） |

**広島では効くが、島根には効かない。**

> **過学習は解けたのに、汎化は改善しない。**
> つまり「広島を暗記していたから島根で落ちる」のではなかった。
> 島根が落ちる理由は別にある。
>
> 一つの仮説をきれいに潰した、という意味で価値のある結果。

## 第3章：U-Net の内部を触る構造を8種類自作した（スライド13〜23）

### スライド13 ― 章の導入

既存構造では差がつかなかった。そこで
**「どの層に何を足せば変わるのか」を切り分けられる形で**自分で構造を作った。

- 自作した構造: **8種類**
- 触った場所: **スキップ / ボトルネック / 統合** の3か所
- パラメータ: 42.3M〜52.7M

> 「良さそうなものを全部盛り」ではなく、**1か所ずつ変えて切り分ける**。
> 実験としてはこちらが正しい。

### スライド14 ― 8つの一覧

| 名称 | 触った場所 | 何をしたか |
|---|---|---|
| 深層監督 1段 | skip2（64×64） | 存在マップの補助ヘッドを付け、1/2 の正解で教える |
| 深層監督 3段 | skip1,2,3 | 3段に監督を入れ、λ を段数で割る |
| 監督Attention | skip2 | 存在マップで skip×(1+attn) と増幅 |
| 同・ブランチ別 | skip2（枝ごと） | 地形量と航空写真で別のヘッドを持つ |
| ASPP | skip2 | dilation 1/2/4/8 + 大域プーリングで受容野を広げる |
| 出力ストライド8 | ボトルネック | 8×8 でなく 16×16 で計算 |
| 出力ストライド4 | ボトルネック | 32×32 まで上げる（**未学習**） |
| 全スケール結合 | デコーダ全段 | 全解像度のスキップを各段に渡す（**未学習**） |

最後の2つは実装・動作確認まで終えたが学習していない。
**前の6つが効かなかったので優先度を下げた**、と正直に書いてある。

### スライド15 ― 仕組み：深層監督と監督Attention

skip2（64×64・256ch）に小さなヘッドを足し、
**「ここに警戒区域があるか」を直接教える**。

```
skip2 (64×64, 256ch)
  │
  ├──→ 補助ヘッド ──→ 存在マップ (64×64, 1ch)
  │     Conv3×3           │
  │     → BN              ├─ (a) 深層監督 ──→ 損失に足す（λ = 0.5）
  │     → ReLU            │      正解を最大プーリングで 64×64 に
  │     → Conv1×1         │      落としたものを教師にする
  │                       │
  │                       └─ (b) 監督Attention ──┐
  │                              sigmoid で 0〜1   │
  │                                                ↓
  └──────────────────── × (1 + それ) ──→ デコーダへ
```

#### BN とは何か

**バッチ正規化（Batch Normalization）。数値のばらつきを揃える層。**

学習は32枚ずつまとめて流す。その32枚ぶんについて、

1. 平均を引く → 平均0になる
2. ばらつきで割る → ばらつき1になる
3. そのあと、学習で決まる倍率とゲタを掛け足す

**テストの点を偏差値に直すのと同じ。** 数学は平均30点、英語は平均80点と
バラバラだと比べにくいが、偏差値に直せば同じ土俵に乗る。

層を何段も重ねると数値が暴れるので、各段で揃えると学習が速く安定する。
いまの CNN ではほぼ標準装備。

補助ヘッドの4段はこうなっている。

| 段 | やること |
|---|---|
| Conv 3×3 | 周り3×3画素を見て 256ch → 64ch に要約 |
| **BN** | 数値のばらつきを揃える |
| ReLU | マイナスを0にする（これが無いと何段重ねても1段と同じ） |
| Conv 1×1 | 64ch → 1ch に潰し、1枚の地図にする |

#### (a) と (b) はどうつながっているか

**分岐ではない。同じ1枚のマップを、2つの用途に同時に使っている。**

- **(a) は教える側** —「このマップを正しく描けるようになれ」と損失で縛る
- **(b) は使う側** —「そのマップを頼りに、本線の強弱をつける」

コードでは、同じ `logits` が2行で使われている。

```python
logits = self.aux_heads[str(st)](skips[st])
aux[st] = logits                                        # (a) 損失へ
skips[st] = skips[st] * (1.0 + torch.sigmoid(logits))   # (b) 変調へ
```

条件によって使い分ける。

| 条件 | (a) | (b) |
|---|---|---|
| 深層監督（DeepSup） | ○ | × |
| 監督Attention（SupAttn） | ○ | ○ |

> **なぜ (a) が必要か。** (b) だけだと、そのマップが何を意味するか誰も
> 教えていない。それがまさに Attention U-Net で、「冗長」に終わった。
> (a) で「これは警戒区域の在りかだ」と**意味を固定**してから (b) で使う、
> というのがこの設計の狙い。

#### なぜ最大プーリングなのか

正解を 128×128 から 64×64 に落とすとき、2×2 の4画素を1画素にまとめる。

- **平均**にすると、小さい箇所が薄まって消える
- **最大**なら「そこに1画素でもあるか」が残る

小さい箇所を拾わせたいのだから、最大でなければ意味がない。

#### 「残差型なので増やす方向にしか働かない」とは

算数で説明できる。

**sigmoid の出力は必ず 0〜1。** だから `1 + sigmoid(...)` は **必ず 1〜2**。

```
skip2 × （1 〜 2）
```

掛ける相手が 1 以上なので、**元の値より小さくなることが絶対にない。**

- ✅「ここは怪しい、強めよう」→ **できる**
- ❌「ここは違う、弱めよう」→ **できない**

> **蛍光ペンは持っているが消しゴムが無い**状態。マークを増やすことしかできない。

**なぜわざとそうしたか。** 素直に `x × sigmoid` にすると、
学習の最初は sigmoid がだいたい 0.5 なので信号が一律に半分に潰れて不安定になる。
残差型なら、役に立たないときモデルは sigmoid を 0 に寄せて
「何もしない（等倍）」に戻せる。**入れても損しない安全な設計。**
MPRNet（Zamir et al., CVPR 2021）も同じ形を使っている。

### スライド16 ― 結果：深層監督と監督Attention

| 施策 | 面積F | 差 | 箇所F | 差 | 予測/正解 面積 |
|---|---|---|---|---|---|
| bg10（この系統の出発点） | 0.6636 | — | 0.6252 | — | 1.512 |
| + 深層監督 1段 | 0.6654 | +0.002 | 0.6404 | +0.015 | 1.598 |
| + 深層監督 3段 | 0.6654 | +0.002 | 0.6412 | +0.016 | 1.573 |
| + 監督Attention | 0.6671 | +0.004 | 0.6449 | **+0.020** | **1.706** |

#### 効いたこと

**100〜3000px の見逃しが減った**（計 −71箇所）。

監督を入れた段の解像度（64×64）で表現できるサイズに効く。
50px 以下は 64×64 では 4×4 画素しかなく、そこまでは届かない。

#### 悪化したこと

**予測が塗り広がった。** 正解の 1.512倍 だった予測面積が **1.706倍** に。

前ページの「増やす方向にしか働かない」がそのまま出ている。

- 箇所F は上がる（+0.020）。太れば正解を覆いやすいので被覆判定を通る
- でも面積の Precision は落ちる。余計な画素が増えるので

> **箇所数では得をして、面積では損をする。**
> だから予測面積比を併記してある。「箇所Fが上がった」とだけ言うのはフェアでない。

#### 段を増やしたら悪くなった理由

3段にしたら、1段版で効いていた改善がむしろ失われた。
**λ=0.5 を段数で割ったため、64×64 への配分が 0.5 → 0.167 に薄まったから。**

段を増やすなら、全体の圧力も増やさないといけなかった。

### スライド17 ― 仕組み：ASPP で受容野を広げる

**受容野**とは「その1画素を計算するのに、元画像のどれだけの範囲を見たか」。

補助ヘッドは Conv 3×3 だけなので、64×64 の段で3画素 = **26.9 m** しか見ていない。
**箇所の典型サイズは 81 m 四方。箇所の3分の1しか見えていなかった。**

#### dilation（飛び飛びの畳み込み）

```
d=1（ふつう）     d=2               d=4
■■■              ■ ■ ■            ■   ■   ■
■■■
■■■              ■ ■ ■            ■   ■   ■
3px 四方
                 ■ ■ ■            ■   ■   ■
                 5px 四方          9px 四方
```

**見る点の数は9個のまま、間隔だけ広げる。**
計算量もパラメータ数も 3×3 のままで、見える範囲だけが広がる。

#### ASPP = 見える範囲の違う5本を並べる

64×64 の段では 1画素 = **8.96 m**。

| # | 枝 | 見える画素 | 実寸 | 何を見ているか |
|---|---|---|---|---|
| 1 | 1×1 | 1px | **9 m** | その画素だけ。細かい模様 |
| 2 | 3×3 d=2 | 5px | **45 m** | 斜面の一部 |
| 3 | 3×3 d=4 | 9px | **81 m** | ★**箇所の典型サイズそのもの**（中央値328px） |
| 4 | 3×3 d=8 | 17px | **152 m** | 斜面ぜんぶ＋ふもと |
| 5 | 大域平均プーリング | 全体 | **573 m** | タイル全体の雰囲気（山の中か市街地か） |

```
skip2 (256ch)
  ├→ 1×1          → 64ch ┐
  ├→ 3×3 d=2      → 64ch │
  ├→ 3×3 d=4      → 64ch ├→ 連結(320ch) → 1×1 Conv で 256ch に戻す
  ├→ 3×3 d=8      → 64ch │                      │
  └→ 大域プーリング → 64ch ┘                      │
                                                 ↓
  └───────────────────────────── ＋ ←─────────────┘
              （残差で skip2 に足し戻す）
```

**残差で足す**のは、ASPP が役に立たなければ足す量を0にして
元の skip2 をそのまま使える、という逃げ道を残すため。

#### なぜ dilation なのか

広く見たいだけならプーリングで縮めればいい。**でも縮めると位置が粗くなる。**
TransUNet がまさにそれで失敗した。dilation は **64×64 のまま**広く見られる。

> **TransUNet の大域文脈はボトルネック（8×8）にあり、
> 解像度を失ったあとに足している。dilation は解像度を保ったまま取るので別物。**

#### なぜ 81 m が重要か

急傾斜地警戒区域の指定は「斜面全体の傾斜と高さ」と
「ふもとに守るべき建物があるか」で決まる。
26.9 m では斜面の真ん中しか見ておらず、判断材料が足りない。

### スライド18 ― 結果：ASPP は補助ヘッドだけを劇的に良くした

**補助ヘッド単体の性能（64×64 の存在マップ）**

| | 受容野 | Recall | Precision | F値 |
|---|---|---|---|---|
| 深層監督のみ | 26.9 m | 0.6200 | 0.5367 | 0.5754 |
| **+ ASPP** | **573 m まで** | 0.7139 | 0.6759 | **0.6944** |

**+0.119。診断は完全に正しかった。** 文脈不足で間違っていたのだ、と確認できた。

**ところが本体の出力は +0.009 しか動かない。13倍の差。**

#### この章で一番大きな発見

> **スキップ接続の質を上げても、デコーダはそれを使わない。**
> 「文脈不足」という診断は正しかったが、**文脈を足す場所が間違っていた。**

逆方向からも確かめている。補助ヘッドの予測を本体出力に OR で統合すると、
箇所Precision が **0.750 → 0.300 に崩壊**した。
**信号はあるが鋭くない。**

> ここが研究として一番面白いところ。
> 「改善しなかった」で終わらず、**改善しなかったこと自体が情報になっている。**
> デコーダがどの経路を信用しているかが分かった。

### スライド19 ― 仕組み：ボトルネックの解像度を上げる

ASPP の結果から「デコーダが信用しているのは**ボトルネック経路**のほうだ」と読んだ。
ならばそちらの解像度を上げれば効くはず。

```
従来                        出力ストライド8
128×128  4.5 m             128×128  4.5 m
   ↓                          ↓
 64×64   9.0 m              64×64   9.0 m
   ↓                          ↓
 32×32  17.9 m              32×32  17.9 m
   ↓                          ↓
 16×16  35.8 m              16×16  35.8 m   ← ここで止める
   ↓  ← pool4                     （pool4 を通さない）
  8×8   71.7 m
```

**8×8 では 1画素が 71.7 m。300px 以下の箇所はここで1画素未満になる。**
プーリングを1段抜いて 16×16（35.8 m/画素）で計算する。

#### ただし受容野が半分になる

縮めるのをやめた分、見える範囲が狭くなってしまう。
そこで **dilation=2 で補う**。

| | 計算 | 実寸 |
|---|---|---|
| 従来 8×8 の5画素 | 5 × 71.7 | 358 m |
| 新 16×16 で d=2 の9画素 | 9 × 35.8 | 323 m |

ほぼ同じ範囲を保てる。

**代償: メモリが約4倍になる。** 出力ストライド4（32×32）も実装したが、
ストライド8 が出発点を超えなかったので学習は保留。

### スライド21 ― 仕組み：全スケール結合（実装済み・未学習）

ここまでは「スキップに**何を足すか**」を変えてきた。
最後に「**どう渡すか**」を変える。

UNet3+ の考え方で、**デコーダの各段が全解像度のスキップを受け取る**。

```
従来:  64×64 のスキップ ────→ 64×64 のデコーダ段（同じ大きさだけ）

全結合: 128×128 のスキップ ─┐
        64×64 のスキップ ───┼─→ 64×64 のデコーダ段（全部受け取る）
        32×32 のスキップ ───┤
        16×16 のスキップ ───┘
```

浅い段は縮小、深い段は拡大してから渡す。

| | パラメータ | VRAM (batch 32) | 状態 |
|---|---|---|---|
| ベース（2枝 U-Net） | 43.58M | — | 学習済み |
| 全スケール結合 | 52.66M | 9.26 GB | 未学習 |
| ＋ ブランチ別監督 | 52.81M | 9.39 GB | 未学習 |
| ＋ ブランチ別 ASPP | 53.36M | 10.58 GB | 未学習 |

> **畳み込みの順番を誤ると1ステップ 24.6 秒かかった。**
> 先に縮めてから畳み込むか、畳み込んでから縮めるかで計算量が桁違いになる、
> という実装上の落とし穴。

### スライド22 ― 損失関数：小さい箇所を重く扱う

画素単位で平均を取ると、**小さい箇所は大きい箇所に比べて 8.45倍 過小評価される**。

```
大きい箇所（1000画素）: 損失に 1000画素ぶん寄与する
小さい箇所（100画素）:  損失に  100画素ぶん寄与する

→ AI は大きい箇所を当てるほうが「得」になる
```

そこで **箇所ごとに重みの総和が揃うよう正規化した損失** を作った。
小さい箇所の1画素を重く、大きい箇所の1画素を軽くする。
強さは `p` で調整する（p が大きいほど強く補正）。

#### 結果：非単調だった

| | 結果 |
|---|---|
| p=0.5 | 箇所F 0.6596（+0.009） |
| **p=1.0** | 箇所F 0.6378（**−0.013、出発点より下**） |

**強くすれば単調に上がるはずなのに、強くしたら下がった。**

p=1.0 は「現状の過小評価 8.45倍 をちょうど打ち消す」設定として選んだのに悪化した。

#### なぜか

> 被覆0.5 を落ちた箇所の **69.4% は「1画素も出ていない」状態**で、
> ロジットが負に張り付いて**勾配が飽和している。重みを8倍しても勾配は0のまま。**

**勾配が0** というのは「どっちに動かせばいいか分からない」状態。
掛け算する重みをいくら大きくしても、0 × 8 = 0 で何も起きない。

重み付けが届くのは「あと少しで当たる画素」だけで、それは **全体の 5.9%** しかない。

> **教訓が書いてある。**
> 「設計の意図どおりに動かない場合、機構より先に**勾配が届いているか**を見るべきだった。」
>
> これは「非単調」という観察から機構の無効性を導いた、良い推論。

### スライド23 ― 背景タイルを学習に混ぜる（bg_ratio）

従来は**警戒区域を含むタイルだけ**で学習していた。
でも実運用では **背景が 61%** を占める。
背景タイルを1割混ぜて、**「出さないこと」も学ばせた。**

| | 広島 面積F | 広島 箇所F | 島根 背景での過検出画素 |
|---|---|---|---|
| bg_ratio = 0（従来） | 0.6727 | 0.6506 | 2,234,652 |
| bg_ratio = 0.1 | 0.6636 | 0.6252 | 2,016,145 |
| 差 | −0.009 | −0.025 | **−218,507** |

#### 狙いは達成、でも F値は下がる

背景での過検出は確かに減った。しかし
**「棄却を学ぶ」ことと「警戒区域を当てる」ことはトレードオフ**で、後者が下がった。

#### 副作用

誤検出の**画素数**は減ったが、誤検出が出る**タイル数**は
島根で 3,848 → **5,456枚に増えた**。

```
before:  濃い誤検出が狭い範囲に      ███
after:   薄い誤検出が広い範囲に  ░░░░░░░░░░░
```

**薄く広がる方向に変わった。** 画素数だけ見ていると改善に見えるが、
「どこかに誤検出が出るタイル」は増えている。

> このスライドの最後の一文が重い。
>
> **「この条件は後にテスト集合の汚染が見つかり、
> 当初『+0.056 で最大の改善』と報告していた値を全面的に訂正した（第6章）。」**

## 第4章：なぜ効かないのかを測った（スライド24〜27）

### スライド24 ― 章の導入

8本の構造改良がどれも動かない。だから
**「どこで失敗しているのか」をタイル単位・層単位で測った。**

> **ここが今期いちばんの収穫**、とスライドに明記されている。

| 数字 | 意味 |
|---|---|
| 282枚 | 1画素も当てられないタイル |
| 61% | そのうち正解が外周16px帯にあるもの |
| 95% | 3条件のいずれかに該当 |

### スライド25 ― まったく当てられないタイルの正体

正解に **1画素も重ならない**タイルが 282枚（2,964枚中 **9.5%**）あった。
その性質を、検出できたタイルと比べた。

| 条件 | 枚数 | 割合 | 検出できたタイルでは |
|---|---|---|---|
| 正解が全部 **外周16px帯**にある | 172 | **61%** | **10.7%** |
| 傾斜コントラストが負（正解の方が緩斜面） | 169 | 60% | 50.9% |
| 小さい（平均 300px 未満） | 235 | 83% | — |
| **いずれかに該当** | 268 | **95%** | — |

#### ① タイルの切り方の問題（61%）

```
┌────────────────┐
│░░░░░░░░░░░░░░░░│ ← 外周16px帯（面積の43.75%）
│░░┌──────────┐░░│
│░░│          │░░│
│░░│  中心     │░░│
│░░│  96×96   │░░│
│░░└──────────┘░░│
│░░░░░░░░░░██░░░░│ ← 正解がここにしかない
└────────────────┘
```

**失敗タイルの 61% は、正解がタイルのふちにしかない。**
検出できたタイルでは 10.7% なので、**6倍の偏り**。

箇所が隣のタイルにまたがって切れてしまっている。
AI には「端っこの切れ端」しか見えていない。

#### ② 入力に答えが無い問題（60%）

**60% は、正解領域のほうが周囲より緩斜面**（中央値 −1.410°）。

**地形量からは「ここが危険」と判断できない。**

> 急傾斜地の指定は「斜面の傾き」だけで決まるわけではなく、
> 「ふもとに守るべき建物があるか」も効く。
> でも AI は建物の情報を持っていない。
> **入力に答えが入っていないのだから、どんなモデルでも当たらない。**

#### 結論

> 失敗の大半は**モデルの表現力不足ではなく**、
> **問題の与え方（①）と入力の不足（②）**で説明できる。

### スライド26 ― 情報はエンコーダでは失われていない

当初は「最初の CNN やボトルネックで小さい箇所の情報が消えている」と考えていた。
各段の活性について、**正解領域と周囲のコントラスト**を測って確かめた。

> 1.0 を超えていれば「失敗タイルのほうがコントラストが強い」

| 段 | 比 |
|---|---|
| enc2 | **1.04倍** |
| enc3 | **1.37倍** |

**予想は外れた。**
失敗タイルでも、活性のコントラストは検出できたタイルと**同等かむしろ高い**。

> **エンコーダは「そこに何かある」ことを捉えている。**
> **情報が消えているのではなく、デコーダがそれを出力に変換できていない。**

この測定で当初の見立てが主因でないと分かり、
以降は**受容野と統合のしかた**に狙いを移した。

> 仮説を立て、測り、外れたことを認めて方針を変える。研究の手順として正しい。

### スライド27 ― クラス不均衡は問題の立て方が違った

**クラス不均衡**とは、正解（警戒区域）の画素が全体のごく一部しかないこと。
ふつうは「だから当たらない」と考える。

| 学習に使った集合 | 正例の割合 |
|---|---|
| 警戒ありタイルのみ（従来） | 9.33% |
| bg_ratio = 0.1 | 5.22% |
| 背景込み全 38,148枚（実運用の分布） | **1.05%** |

正例を重く扱う箇所正規化損失は ±0.004 でほぼ無効だった。
**正例が少ないことが問題なら、ここが効くはず。**

#### 実態

> **「正例が少ない」のではなく「負例の多様性が足りない」。**

| 根拠 | 内容 |
|---|---|
| 1 | bg_ratio は正例の割合を 9.33% → 5.22% に**下げた**（不均衡を**悪化**させた）のに、背景での過検出は**確実に減った**。負例を見せたことが効いている |
| 2 | 逆に正例を重くする損失は非単調で、強めると下がった。**正例側に伸びしろが無い** |

**不均衡を悪化させたほうが良くなった**、というのが決定的。
「不均衡だから当たらない」という説明では説明できない。

#### この診断の使いみち

> 疑似データで正例を増やす方向は、**優先度が低い**。
> むしろ実運用の分布（正例 1.05%）に近い**負例をどう見せるか**が課題。

これは次に何をするかを変える、実用的な結論。

## 第5章：唯一効いたもの ― オーバーラップ推論（スライド28〜31）

### スライド28 ― 章の導入

> 失敗の 61% が「正解がタイルの外周にある」なら、**タイルの切り方を変えればよい。**
> **学習はやり直さず、推論のやり方だけを変えた。**

| 数字 | 意味 |
|---|---|
| +0.047〜+0.060 | 箇所F の改善 |
| 学習不要 | 既存の重みに後から適用できる |
| 282 → 163 | 当てられないタイルが減った |

### スライド29 ― 仕組み：オーバーラップ推論

```
対象タイルと、その周り8枚を貼り合わせる（384×384）

┌────┬────┬────┐
│ NW │ N  │ NE │
├────┼────┼────┤
│ W  │対象│ E  │      そこから 64px ずつずらした
├────┼────┼────┤      9つの窓（128×128）で推論する
│ SW │ S  │ SE │
└────┴────┴────┘
```

**窓をずらすと、外周にあった箇所がどれかの窓では中心に来る。**

```
元の切り方:  ┌──────┐      ずらした窓: ┌──────┐
             │      │                   │      │
             │      │                   │  ██  │ ← 中心に来た
             │    ██│ ← ふち             │      │
             └──────┘                   └──────┘
```

#### 統合のしかた

9つの窓がそれぞれ予測を出すので、1枚にまとめる必要がある。
**中心ほど重い cos 窓で平均**する。窓の端の不確かな予測を弱める。

#### 細かい条件

- 広島の全38,148タイルは格子に**重複なく**載るので、近傍の貼り合わせが成立する
- 8近傍が揃うタイルは **93.9%**。欠けた近傍は中央タイルの鏡像で埋める
- 代わりに **推論コストは9倍**になる

### スライド30 ― 結果

| 条件 | 従来 面積F | OL 面積F | 従来 箇所F | OL 箇所F | 箇所F の差 |
|---|---|---|---|---|---|
| FinalFusion_SAM_APM（出発点） | 0.6727 | 0.6937 | 0.6513 | 0.6984 | **+0.047** |
| bg_ratio = 0.1 | 0.6543 | 0.6799 | 0.6135 | 0.6736 | **+0.060** |
| bg10 + ASPP + ストライド8 | 0.6610 | 0.6815 | 0.6250 | 0.6780 | **+0.053** |

| 数字 | 意味 |
|---|---|
| +0.047〜+0.060 | **どの重みでも効く** |
| 103 / 172 | 境界で切れた箇所の救済（**59.9%**） |
| 93.9% | 8近傍が揃うタイル |

> **学習側のどの改良（±0.01）よりも一桁大きく、しかも再学習が要らない。**
> **モデルではなくタイルの切り方が最大のボトルネックだった。**

### スライド31 ― 統合のしかたで結果が大きく変わる

9つの窓をどうまとめるか。ここを誤ると効果が消える。

| 規則 | 問題 |
|---|---|
| **単純平均** | 境界付近の予測が薄まり **Recall が落ちる** |
| **最大** | どれか1窓の誤検出を拾い **Precision が落ちる** |
| **cos 窓（採用）** | 中心ほど重く平均する。窓の端の不確かな予測を弱める |

> **差は 0.047 あり、施策そのものの効果と同じ大きさ。**
>
> **「やり方を変える」施策では、ハイパーパラメータ1つが施策の有無と同じだけ効く。**

なお、この比較は当時のテスト集合（**汚染あり**）で測ったので絶対値は高めに出ているが、
**規則どうしの大小関係は変わらない**、と断ってある。

## 第6章：研究の進め方で学んだこと（スライド32〜34）

### スライド32 ― 章の導入

> 結果そのものと同じくらい大きかったのが、**実験の管理のしかた**。
> 途中で、**報告していた値が間違っていたことが分かった。**

| 数字 | 意味 |
|---|---|
| 58.9% | テスト集合に混ざっていた学習タイル |
| 約 0.07 | 過大に出ていた F値 |
| 2つ | ひっくり返った結論 |

### スライド33 ― テスト集合の汚染

#### 何が起きたか

**テスト用のデータに、学習に使ったデータが混ざっていた。**

これは絶対にやってはいけない。「答えを見ながらテストを受けた」のと同じで、
点数が意味を持たなくなる。

#### なぜ起きたか

データを訓練/検証/テストに分けるのに `train_test_split` を使っている。
これは **要素数に依存する**ので、同じ `random_state=42` でも
**対象が違えば別の分割になる。**

| | 分割の対象 | できるテスト集合 |
|---|---|---|
| 学習ノートブック（正） | 背景込み 17,149件 | 警戒2,946 + 背景484 = 3,430枚 |
| 評価スクリプト（誤） | 警戒ありのみ 14,816件 | 2,964枚 |

**分割ロジックが2か所にあって、食い違っていた。**

結果、評価に使った 2,964枚のうち **1,746枚（58.9%）が学習に使ったタイルだった。**

#### どれだけ影響したか

| 条件 | 訂正前（誤） | 訂正後 | 差 |
|---|---|---|---|
| bg_ratio = 0.1 | 0.7285 | 0.6636 | **−0.065** |
| bg10 + ASPP + ストライド8 | 0.7403 | 0.6706 | **−0.070** |

**ひっくり返った結論:**
- 「bg_ratio が最大の改善」→ 誤り（実際は −0.009 の悪化）
- 「ストライド8 が唯一 bg10 を超えた」→ 誤り

汚染していた評価 58件を削除し、分割ロジックを修正して**全条件を測り直した**。
まとめ資料も全面改訂した。

> **これを隠さずスライドに載せているのが、この発表の一番立派なところ。**
> 間違いを見つけて自分から訂正するのは、研究者として最も大事な態度。

### スライド34 ― 再発を防ぐために直したこと

| 問題 | 対策 |
|---|---|
| **テスト集合の定義が2か所にあった** | 本来は共通ライブラリに1つ置いて両方から呼ぶべき |
| **config が効いていなかった** | エポック数と bg_ratio がノートブックに直書きされ、設定ファイルが無視されていた。設定から読むよう全ノートブックを修正 |
| **結果を1件1ファイルで残す形にした** | 条件・機械・日時・テスト集合・評価方式を JSON で保存し、そこから表を組み立てる。いま614件。重複IDの検査も入れた |
| **早期終了を入れた** | 最良エポックは 41〜73 だった。**1000エポック回していた時間の8割以上が無駄** |

さらに運用面。

- 2台のPC（Ubuntu / Windows）でブランチを分けて**並行に学習**し、PR 経由で統合
- 重みは外部SSDに置き、リポジトリには入れない（容量が大きすぎるため）

> **「同じ情報が2か所にあると、いつか食い違う」** というのが教訓の核心。
> プログラミング一般に通じる原則（Single Source of Truth）。

### スライド36 ― 分かったこと

| # | 分かったこと |
|---|---|
| 1 | **U-Net の内部をどう触っても ±0.01 しか動かない**。6か所を触ったが、どれも律速ではなかった |

### スライド37 ― 次にやること

| 順 | やること | 根拠 |
|---|---|---|
| 1 | オーバーラップ推論を**島根でも**測る | 広島で +0.047〜+0.060。近傍に学習タイルが含まれる影響を外す必要がある |

> **3 と 4 は「入力を増やす」方向。**
> 学習側の工夫が一通り尽きた以上、**入力に無い情報を足すしか残っていない**、
> というのがここまでの結論。

これはスライド4（航空写真を足すと +0.08〜0.20）に戻ってくる。
**最初に示した事実が、最後の方針になっている。**
