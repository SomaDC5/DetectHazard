# 使い方

`README.md` が全体像。こちらは**ファイルごとの役割**と**作業手順**。

## 0. 最初の準備（新しいPCで1回だけ）

```bash
git clone https://github.com/SomaDC5/DetectHazard.git
cd DetectHazard
conda env create -f environment.yml
conda activate dc5
```

**PyTorch は別に入れなくてよい。** conda-forge の `torchvision` が連れてくる。
GPUのあるPCでは CUDA ビルド、Mac では MPS の使えるビルドが入る。

GPUのあるPCでは、入ったビルドが自分のGPUに対応しているかだけ確かめる。

```bash
python -m dc5lib.device                                      # cuda が選ばれるか
python -c "import torch; print(torch.cuda.get_arch_list())"  # 自分の sm_XX があるか
```

`sm_XX` が無いと `is_available()` は True のまま実行時に落ちる。
世代と必要な CUDA の対応表、入れ直すときの注意は README「2. 最初にやること」。

外部SSDを挿して確認する。

```bash
python -m dc5lib.paths      # SSDが見つかるか
python -m dc5lib.registry   # 条件一覧と重みの有無
python tools/check.py       # 構成の健全性
```

`python -m dc5lib.paths` の出力例。

```
repo         : /home/hirok/DetectHazard
machine      : lab-ubuntu  (linux)
dc5-data     : /media/hirok/SSD-PHPU3A/dc5-data  ssd_id=A ←使用
  weights      あり   項目数 51
```

見つからないときだけ環境変数で指定する。

```bash
export DC5_DATA=/media/$USER/SSD-PHPU3A/dc5-data   # Ubuntu
set DC5_DATA=D:\dc5-data                            # Windows
export DC5_SSD_ID=A                                 # SSDを2台挿しているとき
export DC5_MACHINE=lab-ubuntu                       # 結果に記録される機械名
```

## 1. ファイルごとの役割

### dc5lib/ — 全PC共通のコード

| ファイル | 何をするもの | 単体で実行 |
|---|---|---|
| `paths.py` | **SSDの場所を自動解決。** 場所を知っているのはここだけ | `python -m dc5lib.paths` |
| `registry.py` | `experiments/*/config.yaml` から条件一覧を組み立てる | `python -m dc5lib.registry` |
| `regions.py` | `regions.yaml` から地域一覧を読む | `python -m dc5lib.regions` |
| `models.py` | モデル定義6クラス。重みをそのまま読めるよう層名は不変 | — |
| `data.py` | pkl読込・マスク前処理・分割の再現 | — |
| `results.py` | 精度の記録と `metrics.csv` の生成 | — |
| `sync.py` | 2台のSSDの突き合わせ | `python -m dc5lib.sync status` |
| `instance_eval.py` | 箇所数評価（被覆方式） | `python -m dc5lib.instance_eval` |
| `instance_loss.py` | 箇所正規化した Focal Tversky Loss | `python -m dc5lib.instance_loss` |

`instance_eval.py` と `instance_loss.py` は**自己テスト付き**。組み込む前に単体で走らせて、
期待どおりの挙動か確認できる。特に `instance_loss.py` は
「重みを渡さないとき現行の損失と完全一致すること」を検証する。

主な関数。

```python
from dc5lib.paths import weights_path, checkpoint_path, dataset_path, curve_path
weights_path("FinalFusion_SAM_APM")          # dc5-data/weights/<条件>/best_model.pth
checkpoint_path("FinalFusion_SAM_APM")       # dc5-data/checkpoints/<条件>/...
dataset_path("Hiroshima", "hiroshima_sam_apm.pkl")
curve_path("FinalFusion_SAM_APM")            # results/curves/<条件>.csv
cache_dir("analysis", "tiles")               # 再生成できる中間物の置き場

from dc5lib.registry import load_all, get
c = get("FinalFusion_SAM_APM")
c.arch, c.family, c.inputs, c.n_inputs, c.in_channels, c.augment
c.weights, c.pkl_for("Hiroshima"), c.display()
```

### experiments/ — 条件ごとのノートブック

```
experiments/<条件名>/
├── config.yaml     条件の定義（唯一の正）
├── *.ipynb         学習・評価ノートブック
└── .ipynb_checkpoints/   （gitignore）
```

ノートブックの冒頭に **dc5 共通設定セル** が自動挿入してある。ここで
`CONDITION` と各種パス関数が定義されるので、以降のセルはパスを直接書かない。

### analysis/ — タイル単位の再解析

学習とは別に、保存済みの重みで推論をやり直し、1タイルずつ集計するツール。

| ファイル | 内容 |
|---|---|
| `config.py` | dc5lib からパスと条件を引く読み替え層。**条件のリストは持たない** |
| `data.py` | タイル集合の構築（地域ごとの対象タイルは `regions.yaml` の `subset` に従う） |
| `infer.py` | 推論して1タイル1行の混同行列を作る |
| `features.py` | タイルの性質（正解の形・傾斜・起伏・位置） |
| `instances.py` | 箇所数評価（3方式の比較つき） |
| `analyze.py` | 条件横断の集計・対比較・層別・誤差分解 |
| `run_*.py` | 上記を回す実行スクリプト |

```bash
python analysis/run_inference.py --region all --verify   # 推論（全条件・全地域）
python analysis/run_features.py  --region all            # タイルの性質
python analysis/run_instance_eval.py --region both --save-instances
python analysis/run_attention.py --region hiroshima      # Attentionの注意係数
python analysis/run_analysis.py                          # 集計・図・レポート
```

出力は `dc5-data/cache/analysis/` に出る（数GBになるのでリポジトリには入れない）。

### results/ — 精度の一括管理

| ファイル | 内容 |
|---|---|
| `metrics.csv` | **★ ここを見れば全部わかる。** 1行 = 1評価 |
| `runs/<run_id>.json` | 1学習。`run_id = <条件>__<機械名>__<日時>` |
| `evals/<eval_id>.json` | 1評価 |
| `curves/<条件>.csv` | 学習曲線（旧 losses.csv） |
| `ssd_manifests/<id>.csv` | どのSSDにどの重みがあるか |

**2台のPCで同時に書いても衝突しない。** ファイル名に機械名と日時が入るため。
`metrics.csv` は生成物なので、衝突したら手で直さずに作り直す。

```bash
python tools/make_metrics.py
```

### tools/ — 保守用

| ファイル | 用途 |
|---|---|
| `check.py` | コミット前の検査。異常があれば終了コード1 |
| `make_metrics.py` | `metrics.csv` を作り直す |
| `migrate_to_dc5data.py` | 重み・データをSSDへ移す（済み。`--undo` で戻せる） |
| `rewrite_notebook_paths.py` | ノートブックのパスを dc5lib 経由に直す（済み） |
| `import_existing_results.py` | 過去の解析結果を results/ に取り込む（済み） |
| `dataset_build/` | GeoTIFFから .pkl を作る一式。**3チャネル（地質図）にも対応済み。** 使い方はそのフォルダの README |

## 2. モデルを1つ追加する

### いつ何をするか（2台で並行して作業するので順番が大事）

| 順番 | やること | なぜ |
|---|---|---|
| **⓪ 作業を始める前** | `main` を pull して、**自分のPCのブランチに切る** | main で直接作業しない。2台の変更が混ざる |
| **① コードを書く前** | `git pull` して**名前を決める** | ぶつかるのは名前。決めるこの瞬間に確認する |
| **② 名前を予約する** | `config.yaml` だけ先に commit / push | 相手が pull した時点で名前が見えるので、衝突が起きなくなる |
| ③ | ノートブックを書いて学習する | 重みは自動で SSD に保存される |
| ④ | `sync verify` して commit / push | |
| ⑤ push する直前 | もう一度 `git pull` | 相手のコミットを取り込む（普通の git 作業） |

ブランチは **PCごとに1本**（`lab-ubuntu` / `lab-windows` / `home`。`DC5_MACHINE` と同じ名前）。
main へは PR 経由でマージする。

```bash
git checkout main && git pull
git checkout -b lab-windows        # 既にあれば -b を外す
```

**①を学習コードを書いたあとにすると、衝突が見つかったとき4か所を直すことになる。**
フォルダ名・`config.yaml` の `name`・ノートブックの `CONDITION`・
（学習済みなら）`dc5-data/weights/<条件名>/`。

②を挟むのが効く。長い学習を始める前に名前だけ push しておけば、
相手が同じ名前を選ぶことがなくなる。コストはゼロ。

### ①と②を1コマンドで

```bash
python tools/new_experiment.py FinalFusion_SAM_APM_bg30 \
    --from FinalFusion_SAM_APM --bg-ratio 0.3 --note "背景タイルを3割混ぜた版"
```

これが自動でやること。

1. `git fetch` して、**ローカルにも他のリモートブランチにも**同名が無いか調べる
   （相手のPCがまだマージしていないブランチの名前も見る）
2. 大文字小文字だけ違う名前も弾く（Ubuntu と Windows/exFAT で壊れるため）
3. `config.yaml` を作り、ひな形のノートブックを複製して `CONDITION` を差し替える
4. `--from` が旧プロトコル（検証分割なし・テストF値でベスト選択）だった場合は、
   6:2:2 + 検証でのベスト選択に直す（同じ欠陥を繰り返さないため）
5. 名前を予約するコマンドを表示する

使われている名前を見るだけなら `python tools/new_experiment.py --list`。

弾かれたときはこう出る。

```
「MiddleFusion_DEM_APM」は使えません。
  - 大文字小文字だけが違う条件があります: MIddleFusion_DEM_APM
    （Ubuntuでは別物、Windows/exFATでは同じ扱いになり壊れます）
```

### config.yaml を書く

`name` は**フォルダ名と一致させる**（`check.py` が検査する）。

```yaml
name: FinalFusion_SAM_APM_bg30      # フォルダ名と同じ
arch: MultiEncoderUNet              # dc5lib/models.py のクラス名
family: Final                       # 図表のグループ分けに使う
inputs:
  - {key: terrain,  source: SAM, channels: 1, field: DEM}
  - {key: airphoto, source: APM, channels: 3, field: AirPhoto}
augment: false
bg_ratio: 0.3                       # 学習に混ぜる背景タイルの割合
status: active
label: ''                           # 空なら family と inputs から自動生成
note: 背景タイルを3割混ぜた版
dataset:
  Hiroshima: hiroshima_sam_apm.pkl
  Shimane:   shimane_sam_apm.pkl
train:
  epochs: 1000
  batch_size: 32
  lr: 0.0001
  seed: 42
  loss: {type: focal_tversky, alpha: 0.7, beta: 0.3, gamma: 0.75}
  augment_params: null
```

### 損失を変える場合（モデルは変えない）

**損失を変えたいときに `--arch` を触る必要はない。** 箇所正規化損失を入れても
U-Net の構造は一切変わらず、変わるのは `train.loss` だけ。

```bash
python tools/new_experiment.py UNet_SAM_InstLoss \
    --from Train_Hiroshima_Test_Shimane_OnlySAM \
    --loss instance_weighted_focal_tversky --p 0.5 --a0 300 --beta 0.5
```

`config.yaml` にこう入る。

```yaml
train:
  loss:
    type: instance_weighted_focal_tversky
    alpha: 0.7        # False Negative（見逃し）の重み
    beta: 0.5         # False Positive（過検出）の重み。箇所重みで見逃し側が
                      # 強まるぶん、既定の 0.3 より上げてある
    gamma: 0.75
    a0: 300           # 面積の下限。小さい箇所の重みが発散するのを防ぐ
    p: 0.5            # 重みの強さ。0 で無効、1.0 で完全な箇所正規化
    center_lam: 0.0   # 中心重み。まず 0 で、箇所正規化の効果を見てから足す
```

ノートブック側は自動で差し替わる。

```python
criterion, NEEDS_WEIGHT = build_loss(CONDITION)   # config.yaml が効く
```

対応している損失と既定値は `python -m dc5lib.losses`、
ある条件が何を使っているかは `python -m dc5lib.losses <条件名>` で見られる。

**箇所正規化損失は重みマップを必要とする**（`NEEDS_WEIGHT == True`）。
`--loss instance_weighted_focal_tversky` を指定すると、ノートブックの冒頭に
残り3箇所の手順を書いた注意セルが自動で挿入される（入力数に合わせた書き方になる）。

手順書がある。

- `docs/解析ツールの解説.md` … analysis/ と tools/ の各スクリプトの使い方と仕組み
- `docs/練習_新しい条件を作る.md` … 基本の8ステップ（確認コマンドつき）
- `docs/練習_SAM_APM_MultiEncoder_箇所損失.md` … SAM+APM / MultiEncoderUNet /
  箇所正規化損失 を作る手順。指定できる引数を全部明示した版で、
  手作業になる配線6箇所もセル番号つきで書いてある

実装済みの例が `experiments/UNet_SAM_InstLoss/` にある。
重みマップの事前計算・`JointTransform` への追加・`Dataset` と学習ループへの
受け渡しまで入っていて、新しく作るときはこれを `--from` にするのが早い。

```bash
python tools/new_experiment.py UNet_SAM_InstLoss_p10 \
    --from UNet_SAM_InstLoss --p 1.0
```

### デバイスの選択

ノートブックは `pick_device()` を使う（`cuda` → `mps` → `cpu` の順）。
研究室PCでは CUDA、Mac では MPS が選ばれる。`DC5_DEVICE=cpu` で固定もできる。

```bash
python -m dc5lib.device      # 何が選ばれるか確認
```

### アーキテクチャを指定する

`--arch <クラス名>`。指定できるのは `dc5lib/models.py` の `MODEL_CLASSES` に
登録されているものだけ。

```bash
python -m dc5lib.models      # 一覧
```

```
クラス名                        forward の引数               入力数
UNet                        (x)                       1
MultiEncoderUNet            (dem, air)                2
EarlyFusionUNet             (dem, air)                2
MiddleFusionUNet            (dem, air)                2
AttentionMultiEncoderUNet   (dem, air)                2
TransUNetDual               (dem, air)                2
```

**`--arch` を変えるときは `--inputs` と `--family` も揃える。** 3つは連動する。

```bash
# 単一入力に変える（3つとも変える）
python tools/new_experiment.py UNet_SAM_x --from FinalFusion_SAM_APM \
    --arch UNet --family Single --inputs SAM
```

`--family` は図表のグループ分けにしか使わないので、精度には影響しない。
`--inputs` は `SAM` / `SAM+APM` / `SAM+APM+GEO` のように書く。

食い違いは作る前に止まる。

```
! 入力数が合いません。UNet.forward は 1 入力ですが、inputs は 2 個（SAM+APM）です。
  --inputs か --arch を見直してください。
```

`--inputs` を変えたら **`config.yaml` の `dataset` も見直すこと。**
ひな形の pkl が残っていると警告が出る。

```
! Hiroshima の pkl 'hiroshima_sam_apm.pkl' は航空写真を含みますが、
  inputs には入っていません。読み込みが無駄に重くなります。
```

逆に、入力にあるものが pkl に無い場合は `check.py` が止める
（学習中に落ちるより先に気づける）。

```
- T6: inputs に航空写真があるのに、Hiroshima の pkl 'hiroshima_sam.pkl' には
      含まれていないようです
```

### 新しいモデルクラスを足すなら

`dc5lib/models.py` にクラスを書いて `MODEL_CLASSES` に登録する。

```python
class MyNewUNet(nn.Module):
    def __init__(self, out_channels=1): ...
    def forward(self, dem, air): ...        # 引数の数が入力数になる

MODEL_CLASSES = {..., "MyNewUNet": MyNewUNet}
```

登録前に `--arch MyNewUNet` を指定しても作成はできるが、その場で警告が出る。

```
! モデルクラス「MyNewUNet」は dc5lib/models.py に登録されていません。
  登録済み: UNet, MultiEncoderUNet, ...
  このまま作れますが、学習の前に models.py にクラスを追加して
  MODEL_CLASSES に登録してください。
```

`forward` の引数の数が、そのまま `inputs` に書ける数の上限になる。
3入力にするなら `forward(self, dem, air, geo)` のクラスが要る。

## 2.5 アンサンブルを1つ追加する

**`experiments/` には置かない。** あそこは「1回の学習」の単位で、アンサンブルには
学習が無いため、ノートブック・`arch`・`inputs` を嘘で埋めることになる
（理由は `dc5lib/ensembles.py` の冒頭）。

定義は `ensembles.yaml` の1か所。`regions.yaml` と同じ発想。

```yaml
ensembles:
  Ens_MyMix:
    label: アンサンブル 私の組み合わせ     # 図表に出る名前。重複すると検査で止まる
    note: なぜこの組み合わせか
    members:                              # bg_ratio が揃っていること
      - FinalFusion_SAM_APM
      - AttentionUNet_DEM_APM
    weights: null                         # null で単純平均。[2, 1] のように書ける
    rule: mean                            # mean / max / median
    threshold: 0.5
```

```bash
python -m dc5lib.ensembles                                   # 一覧と検査
python analysis/run_ensemble_eval.py --ensemble Ens_MyMix --region hiroshima
python analysis/run_ensemble_eval.py --ensemble Ens_MyMix --region hiroshima --record
```

`--record` を付けると `results/evals/` に入り、`metrics.csv` に**単一条件と並んで**
載る（`build_metrics_csv` は `evals/` だけを読み、`runs/` と結合していないため）。
`--each` でメンバー単体の値も一緒に出せる。

**`members` の `bg_ratio` は揃えること。** ノートブックは背景タイルを混ぜたあとで
分割するので、`bg_ratio` が違うと `train_test_split` の結果が変わり、タイルが
突き合わない。`tools/check.py` が止める。

| 検査で止まるもの |
|---|
| `members` に無い条件がある / 重複している |
| `bg_ratio` が揃っていない |
| `weights` の数が `members` と合わない / 負の値 |
| 未知の `rule` / `threshold` が 0〜1 の外 |
| 同名の実験条件がある / 表示ラベルが重複している |

`rule` は既定の `mean` から変えないほうがよい。**`max`（OR の連続版）は実測で
最下位**だった（`docs/アンサンブルで解けるか.md` 2.1）。

**手順を1つずつ追うなら `docs/練習_新しいアンサンブルを作る.md`。**
混ぜる条件の選び方（相関・条件数・弱いメンバー）の根拠つき。

メモリに注意。島根24,569枚だと確率マップが1条件 805MB になる。`mean` と `max` は
逐次に足し込むので条件数に依らないが、**`median` は全メンバーを同時に持つ**。

## 3. 地域を1つ追加する（例：岡山）

**① データセットを置く**

```
dc5-data/datasets/Okayama/okayama_sam_apm.pkl
```

**② `regions.yaml` に足す**

```yaml
  okayama:
    dir: Okayama
    label: 岡山
    role: eval        # 学習に使わないなら eval
    subset: all       # 地域内の全タイルを評価に使う
```

**③ 各条件の `config.yaml` に pkl を足す**

```yaml
dataset:
  Hiroshima: hiroshima_sam_apm.pkl
  Shimane:   shimane_sam_apm.pkl
  Okayama:   okayama_sam_apm.pkl      # ← 追加
```

**④ `analysis/features.py` の `FEATURE_PKL` に1行足す**（傾斜の統計を出すため）

```python
FEATURE_PKL = {..., "okayama": "okayama_sam.pkl"}
```

**⑤ 回す**

```bash
python analysis/run_inference.py --region okayama
python analysis/run_features.py  --region okayama
```

コードの書き換えは④の1行だけ。地域名を直書きしている箇所は他にない。

## 4. 3入力以上にする（例：地質図を足す）

`config.yaml` の `inputs` は**いくつでも書ける**。

```yaml
inputs:
  - {key: terrain,  source: SAM, channels: 1, field: DEM}
  - {key: airphoto, source: APM, channels: 3, field: AirPhoto}
  - {key: geology,  source: GEO, channels: 3, field: Geo}
```

`field` は pkl の中の属性名。`registry` は `n_inputs=3`、`in_channels=[1,3,3]` を返す。

**ただし、これだけでは動かない。** 次の3か所に手を入れる必要がある。

| 直す場所 | 内容 |
|---|---|
| `dc5lib/models.py` | 3エンコーダのクラスを追加して `MODEL_CLASSES` に登録。既存6クラスはすべて `forward(self, dem, air)` の2入力固定 |
| `analysis/data.py` の `build_tileset` | いまは `terrain` と `air` の2本だけを読む。`cond.inputs` を回して `field` の属性を読む形にする |
| `analysis/infer.py` の `run_condition` | `if cond.use_airphoto: model(terrain, air)` を `model(*tensors)` にする |

学習ノートブック側は、新しい条件用に1冊コピーして作ることになるので、
そこで3つ目の入力を読む処理を書けばよい。

`Triple_UNet_SAM_APM_GEO` が3入力の実例として `experiments/` に入っている
（`status: excluded`、モデルクラスは未登録）。ここを復活させるのが最短。

**データ側はすでに用意できる。** `tools/dataset_build/build_shimane_dataset_v6.py` に
`--geology` オプションがあり、地質図を含む pkl を作れる。
広島・島根とも `*_sam_apm_geo_final_v2.pkl` が両SSDに存在している。

## 5. 2台のPCで並行して学習する

PC1（Ubuntu・SSD A）とPC2（Windows・SSD B）で**別々のモデルを同時に学習する**のが
通常の使い方。揃えるものは2つある。**SSDだけ揃えても足りない。**

| 何が | どこに出来るか | 揃える手段 |
|---|---|---|
| 重み・チェックポイント | **SSD** `dc5-data/weights/<条件>/` | `sync unify` |
| config.yaml・ノートブック | リポジトリ `experiments/<条件>/` | git |
| 学習曲線・精度の記録 | リポジトリ `results/` | git |

`results/curves/<条件>.csv`（旧 losses.csv）と `results/runs/*.json` は
**SSDではなくリポジトリ側**に出る。ここを忘れると精度の記録だけ揃わない。

### 学習を始める前

```bash
git pull                       # 相手の config やノートブックを取り込む
```

**条件名が相手とかぶらないことを確認する。** 同じ名前で別々に学習すると、
あとで重みがぶつかる（`sync` が検出して止めるが、どちらかを捨てることになる）。
`git pull` したあと `python -m dc5lib.registry` で一覧を見るのが確実。

### 学習が終わったら（各PCで）

```bash
python -m dc5lib.sync verify      # 増えた重みを在庫表に反映（差分のみ再計算、数秒）
git add -A && git commit -m "<条件名> を学習" && git push
```

push 先は自分のPCのブランチ。main へは PR 経由でマージする。

`verify` を忘れると、増えた重みが在庫表に載らず同期で取りこぼす。
忘れても `sync` 側が「在庫表が古いです」と言って止まるので事故にはならない。

### 両方終わったら（SSDを2台とも挿したPCで）

```bash
python -m dc5lib.sync unify /media/$USER/Soma_SSD/dc5-data --run
git pull                          # 相手の commit を取り込む
python tools/make_metrics.py      # metrics.csv を作り直す
git add -A && git commit -m "2台の結果を統合" && git push
```

`unify` は次を自動でやる。

1. 両方の在庫表を更新（差分のみ再ハッシュなので数秒）
2. A → B で足りないものをコピー
3. B → A で足りないものをコピー
4. 在庫表を更新して `results/ssd_manifests/` に書き出す

`--run` を付けなければ確認だけ。チェックポイント（8.7GB）を運びたくないときは
`--weights-only` を付ける。

### 同じ名前の条件を2台で学習してしまったら

`unify` は**黙って上書きしない**。中身が違うファイルを一覧にして止まる。

```
  !! 両方にあって中身が違うファイル: 1 件
      weights/SameName_SAM_APM/best_model.pth
     同じ名前の条件を2台で別々に学習した可能性があります。
     どちらを残すか決めてから、--force を付けるか、片方の条件名を変えてください。
```

対処は2つ。

- **両方残す**（推奨）— 片方の条件名を変える。フォルダ名・`config.yaml` の `name`・
  `dc5-data/weights/<条件>/` の3つを揃えて改名する
- **片方を捨てる** — 残すほうのSSDを src にして `--force` を付ける

どちらを残すか判断する材料は `results/runs/*.json`（機械名・学習日時・best epoch）にある。

### その他のコマンド

```bash
python -m dc5lib.sync check          # 在庫表が実ファイルとずれていないか（終了コードで判定）
python -m dc5lib.sync status         # git上の在庫（SSDを挿さなくてよい）
python -m dc5lib.sync diff  <他方>   # 突き合わせるだけ
python -m dc5lib.sync verify --full  # 全件を再ハッシュ（既定は差分のみ）
```

### いまの2台

| ssd_id | ラベル | Mac でのマウント先 |
|---|---|---|
| A | `SSD-PHPU3A` | `/Volumes/SSD-PHPU3A/dc5-data` |
| B | `Soma_SSD` | `/Volumes/Soma_SSD/dc5-data` |

`dc5-data/` の中身は完全に同一（48ファイル / 65.3GB / sha256一致）。
両方挿したときは `DC5_SSD_ID` で選ぶ。

### 3台目のSSDを用意する

```bash
mkdir -p /path/to/SSD-C/dc5-data/{weights,checkpoints,datasets,cache}
cat > /path/to/SSD-C/dc5-data/.dc5-root.json <<'EOF'
{"schema": 1, "ssd_id": "C", "label": "<ラベル>", "created": "2026-09-27"}
EOF
DC5_SSD_ID=C python -m dc5lib.sync unify /Volumes/SSD-PHPU3A/dc5-data --run
```

`ssd_id` が違えばラベルは何でもよい。自動検出は目印ファイルを探すので、
ドライブレターにもマウント先にも依存しない。

## 6. 困ったとき

| 症状 | 対処 |
|---|---|
| `dc5-data が見つかりません` | SSDが挿さっているか確認。`export DC5_DATA=...` で直接指定 |
| `dc5-data が複数見つかりました` | SSDを2台挿している。`export DC5_SSD_ID=A` |
| `dc5lib が見つかりません` | リポジトリの外で起動している。`cd` してから実行 |
| `metrics.csv` がコンフリクト | 手で直さず `python tools/make_metrics.py` |
| Ubuntu と Windows で全行差分が出る | `.gitattributes` が効いていない。`git add --renormalize .` |
| git の容量が異常に大きい | 外付けSSD(exFAT)上で clone している。クラスタが512KBなので1ファイル最低512KB消費する。**ローカルディスクに clone し直す**。応急処置は `git gc` |
| Mac で触ったあと `._*` が大量発生 | `dot_clean -m <path>`。exFAT にメタデータを書けないため |
| 重みが見つからない | `python -m dc5lib.sync status` でどちらのSSDにあるか確認 |
