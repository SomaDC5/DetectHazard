# 学習ノートブックの作り方（**この文書に沿って作る**）

新しい条件を足すとき、評価を足すとき、`dc5lib` を伸ばすときの決まりごと。
**既存のノートブックをコピーして作らない。** ここから作る。

> **Claude（AI）に作らせるときも、必ずこの文書に沿わせること。**
> リポジトリ直下の `CLAUDE.md` からここを指している。
> 読まずに書き始めた実装は、受け取る前に `tools/check.py` と
> `tools/audit_wiring.py` で落ちる。

なぜこの文書があるか ── `docs/設計図_現状.md` に実測が載っている。
要点だけ繰り返すと、**既存55本のうち30本は `CFG = train_cfg(...)` が無く、
config の `train:` が1項目も届いていなかった。** `bg_ratio` は 0/55、
`batch_size` と `random_state` も 0/55。乱数の固定は12本だけ。
早期終了がループに無いものが23本。**コピーで増やしたからこうなった。**

## 1. 守ること（これだけは例外なし）

1. **値をノートブックに書かない。** すべて `config.yaml` から来る。
   `batch_size=32` と書いた瞬間に、この文書に反している
2. **処理をノートブックに書かない。** `dc5lib` の関数を呼ぶ。
   学習ループを書き写さない（差し込みは `hooks`）
3. **学習と評価を同じノートブックに入れない。**
   `train.ipynb` と `eval_shimane.ipynb` に分ける
4. **検証・テストのタイルを近傍に使わない。**
   `build_loaders` が `allowed_except` でやっているので、
   **自分で `allowed=None` を書かない**
5. **テストで最良エポックを選ばない。** 選択は検証F値。
   `fit()` がそうしているので、自分で選択を書かない
6. **数字を docs に書くときは、出した計算をコードに残す。**
   `analysis/run_building_derived.py` と
   `analysis/run_union_subsets.py` がその例

## 2. 作る手順

### 2.1 条件を作る

```bash
python tools/new_experiment.py <条件名> --from <ひな形> --note "何を試すか"
```

名前の衝突（他のPCの作業中のものを含む）を見てから作る。
**学習を始める前に config だけ push して名前を予約する。**

`config.yaml` に必ず入れるもの。

```yaml
protocol: v3-base        # 基盤ノートブックで学習したもの
ensemble: true           # 和集合に入れてよいか
seeded: true             # 乱数を固定して学習したか
split:                   # 省略すると train: の値で random になる
  kind: random           # random / csv（csv はブロック分割）
  test_size: 0.2
  val_size: 0.25
  random_state: 42
overlap:                 # 省略すると素のタイルで学習する
  max_shift: 64
  seed: 42
```

> **`protocol` を `v3-base` にするのは、本当に基盤ノートブックで
> 学習したときだけ。** 嘘を書くと `ensemble: true` の判断が崩れる。

### 2.2 ノートブックを作る

`python tools/new_experiment.py <条件名>` を **`--from` を付けずに**走らせると、
`templates/train.ipynb` と `templates/eval_shimane.ipynb` から作られ、
`CONDITION` も差し替わる。**`--from` で旧世代をコピーしない。**
いまの雛形は `train.ipynb` が11セル・113行、`eval_shimane.ipynb` が6セル・46行
（既存の `Keisya_airPhoto_final6.ipynb` は41セル・1,640行）。

| セル | 中身 |
|---:|---|
| 0 | markdown。`label` と `note` をそのまま出す |
| 1 | `CONDITION` / `CFG = train_cfg(CONDITION)` / `CFG.describe()` / **config.yaml の全文表示** |
| 2 | `seed_everything(CFG.seed)` |
| 3 | `ld = build_loaders(get(CONDITION), "Hiroshima")` |
| 4 | `print(ld.describe())` ── **検算をここで見る** |
| 5 | `model = build_model_for(get(CONDITION))` と入口のチャネル検算 |
| 6 | `hist = fit(get(CONDITION), ld)` |
| 7 | 曲線を `paths.curve_path` から読んで描く |
| 8 | `print(ckpt.describe(get(CONDITION).weights))` ── **重みの素性** |
| 9 | markdown。次は `eval_shimane.ipynb` |

**`import` は cell 1 にまとめる。** 既存は `import torch` が8回出てくる。

## 3. 分割と近傍 ── データリークをどこで止めているか

```
pkl 38,148 枚
├── 警戒区域あり 14,816 枚（= dataset2）→ 学習 8,889 / 検証 2,963 / テスト 2,964
└── 背景       23,332 枚（= dataset3）→ どの集合にも入らない

近傍を貼る材料 = 38,148 枚ぜんぶ（**背景も使う**）
貼ってよい近傍 = 38,148 − 検証 2,963 − テスト 2,964 = 32,221 枚
```

- **背景タイルを近傍に使うのは漏れではない。** 学習・検証・テストの
  どこにも属さないので、そこを覗いても評価の答えは出てこない。
  使わないと**8近傍が揃うのは 0.2%**しかなく、ずらす幅がほとんど取れない
- **漏れるのは検証・テストのタイルを近傍にしたとき。** ずらす幅は最大
  64px ＝ タイルの半分なので、**窓は隣のタイルの半分まで入る。**
  その隣が検証・テストだと、学習中にその画素を見てしまう
- `build_loaders` は `allowed_except(38148, 検証, テスト)` を使い、
  **混入していないことを例外で止めている。** ここを自分で書き換えない

**新しい分割を試すとき**（`kind: csv` や新しい `kind` を足すとき）は、
`tools/audit_splits.py` で**他の条件と食い違わないか**を必ず測る。
食い違ったら `ensemble: false` にする。

## 4. `dc5lib` の入口（これだけ覚えればよい）

| 呼ぶもの | 役割 |
|---|---|
| `registry.get(CONDITION)` | `config.yaml` → `Condition` |
| `traincfg.train_cfg(CONDITION)` | `train:` → `TrainCfg`（既定値つき） |
| `pipeline.seed_everything(CFG.seed)` | 乱数の固定。**これが無いと `seed` は何も変えない** |
| `pipeline.build_loaders(cond, region)` | pkl → 前処理 → 分割 → `DataLoader` |
| `models.build_model_for(cond)` | `arch` と `inputs` からモデル |
| `losses.build_loss(cond)` | `train.loss` → `(criterion, needs_weight)` |
| `train.fit(cond, loaders)` | 学習・早期終了・曲線・重みの保存 |
| `ckpt.describe(cond.weights)` | 重みの素性 |
| `ckpt.same_split(a, b)` | 2つの重みが同じ分割か |
| `splits.resolve(cond, no, cfg)` | 分割の解決（`random` / `csv`） |
| `paths.curve_path(name)` / `cond.weights` | 置き場。**自分で組まない** |

### 4.1 細工は `hooks` で入れる

```python
hist = fit(cond, ld, hooks={
    "forward":      lambda model, xs: model(*xs),   # 補助出力つきの前向き
    "loss_fn":      lambda out, y: ...,             # 損失の計算
    "on_epoch_end": lambda ep, m: ...,
    "optimizer":    torch.optim.AdamW(...),
    "model":        ...,                            # モデルを自分で作るとき
})
```

**ループを書き写さない。** 書き写すと、早期終了と曲線の flush と
検証での選択を、条件ごとにまた取りこぼす。

## 5. アンサンブル（和集合）

**本研究はこれを多用する。** だから構成員の宣言を1か所に集めてある。

### 5.1 構成員は `ensembles/*.yaml` にだけ書く

```yaml
# ensembles/union5.yaml
name: union5
label: 5本（44。実建物だけの対照も足した）
base: FinalFusion_SAM_APM_OverlapTrain      # 比較の基準になる構成員
members:
  - FinalFusion_DEM_APM_OverlapTrain
  - FinalFusion_SAM_APM_LU_OverlapTrain
  - FinalFusion_SAM_APM_BVB_OverlapTrain
  - FinalFusion_SAM_APM_BLD_OverlapTrain
recorded: docs/展望_再現率をどう上げるか.md 44.4   # 数字が載っているなら動かさない
note: 床が 491件(5.47%) / 3,377件(12.30%)。
```

**コードに構成員の名前を書かない。** 以前は

    analysis/run_stage2_room.py   STAGE1 / UNION3
    analysis/run_miss_overlap.py  DEFAULT
    tools/audit_splits.py         DEFAULT

の3か所に別々に並んでいて、**どれかを足し忘れると「測った集合」と
「語っている集合」が食い違った。** いまは全部 yaml から読む。

> **`recorded:` が書いてある定義は動かさない。** その集合で出した数字が
> docs に載っているので、構成員を変えると過去の記述が嘘になる。
> 構成員を変えたいときは**新しい yaml を作る**。

### 5.2 混ぜる前に検査する

```bash
python -m dc5lib.ensemble union5        # 一覧と検査の結果
```

`dc5lib.ensemble.verify(e)` が止めるもの。

| | |
|---|---|
| 構成員が実在しない / 重みが無い | 例外 |
| **`ensemble: false` が入っている** | 例外。いまそれは `FinalFusion_SAM_APM_BlockSplit`（別の土俵）と `Train_Hiroshima_Test_Shimane_SAM_APM`（テストで最良エポックを選んでいる） |
| **分割が食い違っている** | 例外 |
| 分割が重みから分からない | 止めない。**「分からない」と言って `tools/audit_splits.py` を促す** |
| 全員の入力が同じ | 止めない。警告だけ |

分割の照合は**重みの素性**（`meta.split.fingerprint`）を見るので
**pkl を読み直さない。** 素性の無い古い重みでは分からないので、
そのときは `tools/audit_splits.py` で pkl から確かめる（広島+島根で5分）。

### 5.3 測るときは雛形を使う

```bash
jupyter lab templates/ensemble.ipynb      # ENSEMBLE = "union5" を書き換える
```

7セル。**数字はスクリプトに出させる** ── `42`〜`44` を出した
`analysis/run_union_blind.py` と `analysis/run_union_subsets.py` を
そのまま呼ぶので、ノートブックが別に計算して食い違うことがない。

| セル | 中身 |
|---:|---|
| 1 | `ENSEMBLE = "union5"` と `ensemble.report()` |
| 2 | `ensemble.verify(e)`（だめなら例外） |
| 3 | **素性の無い構成員が1本でもあれば pkl から分割を確かめる**（食い違えば止まる） |
| 4 | `run_union_blind.py`（単体・和集合・床・天井・面積層別・合意数） |
| 5 | `run_union_subsets.py`（部分集合の床と Jaccard。推論しない） |

### 5.4 読み方 — **成否は床で見る**

| 見るもの | 意味 |
|---|---|
| **床** | どの構成員も1画素も光らない正解の割合。**ここが下がったかで決める** |
| 天井（1 − 床） | 構成員を増やして届きうる上限 |
| 刈り取り後の上限 箇所F | `2R/(1+R)` |
| 和集合の箇所F | **上がらないのが普通。** 価値は上限にある（`42.1`） |
| Jaccard | 1 に近いほど同じ場所を光らせている |

ゆらぎ幅（広島 箇所F 0.0071 / 島根 0.0198）より小さい差は「差が無い」。

> **種だけ違う2本目も手札になる。** 入力を変えずに同じ条件を別の種で回しただけで、
> 床は広島 5.3% / 島根 5.1% 下がった ── **別の入力を足したときの約半分**
> （`展望_再現率をどう上げるか.md` の `44.8`）。手札の入力が思いつかないときの逃げ道。
> ただし**何本で飽和するかは未検査**である。

**一方、「仮想建物あり vs なし」のように入力の違う2本を比べるときは、種の
ゆらぎと区別がつくかを必ず確かめること。** `44.7` ではJaccard 0.482 の食い違いが
仮想建物のせいに見えたが、**同じ条件を種だけ変えた2本の Jaccard も0.514 で、** 
区別がつかなかった。**比べたい差と同じ大きさのゆらぎが種にある。**

## 9. 長い学習は `tools/run_training.py` で回す

```bash
python tools/run_training.py <条件名>                  # 本番
python tools/run_training.py <条件名> --epochs 1 --dry  # 試運転（別の場所に書く）
```

**中身はノートブックと同じで、`dc5lib` の同じ関数を同じ順に呼ぶだけである。**
手順を二重に持っていない。分割の期待値の照合（`2.3`）もここに入っていて、
**違ったら学習を始めずに止まる。**

> **なぜノートブックで回さないか。** `nbconvert --execute` で
> **カーネルが何も出力せずに消えることがあった**（2026-10-29）。
> メモリは 10GB 以上空き、GPU も空き、同じコードは平文のプロセスで通る。
> **同じセル構成でも通るときと死ぬときがあり、原因は特定できていない。**
> 2時間の学習を最後のセルで失うのが最悪なので、長い学習は実行器から回す。
> ノートブックは対話で見るため・雛形として残してある。

## 6. まだ通っていない道（**使う前に実データで確かめる**）

- **`bg_ratio > 0`。** `pipeline.build_loaders` は
  `NotImplementedError` を投げる。既存の背景混ぜは `dataset3` から
  `random.seed(CFG.seed)` で選ぶ手順で、**再現を確かめずに書くと
  黙って違うものを学習する。** 必要になったら実データで照合してから入れる
- **重みマップが要る損失**（`instance_weighted_focal_tversky`）。
  `fit()` は `hooks["loss_fn"]` が無ければ例外で止まる。
  `docs/使い方.md` の手順で重みマップを作り、`loss_fn` で渡す
- **`AttentionUNet_SAM_APM256`** のような高解像度の条件。
  入力の大きさが 128 でないので、検算の値が上の表と違う

## 8. 出す前の確認

```bash
python tools/check.py            # import・3x3の向き・巨大ファイル
python tools/audit_wiring.py     # config が届いているか／直書きとの食い違い
python tools/audit_splits.py --region both   # 分割が他と一致しているか
```

**`audit_wiring.py` の「直書きの値が config と違う」は 0 件でなければならない。**
いま 0 件である。1件でも増やしたら、その条件は信用できない。

新しいノートブックは、さらにこれを満たす。

- `CFG = train_cfg(...)` がある
- `seed_everything` を呼んでいる
- `build_loaders` / `fit` を使っている（ループを書き写していない）
- 値の直書きが無い（`audit_wiring.py` の行が「経由」だけ）
- `ckpt.describe(cond.weights)` が素性を出す
