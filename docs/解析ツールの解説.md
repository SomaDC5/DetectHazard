# 解析ツールの解説

`analysis/` と `tools/` に何があって、何をしていて、どう使うか。
コードを読む前の見取り図として書いてある。

---

## 0. 全体の流れ

```
         学習（ノートブック）
                │  重み → dc5-data/weights/<条件>/best_model.pth
                ▼
 ┌─────────────────────────────────────────────────┐
 │ analysis/  保存済みの重みで推論をやり直し、タイル単位に分解 │
 │                                                  │
 │  run_inference.py      1タイル1行の混同行列                │
 │  run_features.py       タイルの性質（正解の形・傾斜・位置）   │
 │  run_instance_eval.py  箇所数評価                        │
 │  run_attention.py      Attention の注意係数               │
 │         ↓ すべて dc5-data/cache/analysis/ に出る           │
 │  run_analysis.py       条件横断の集計・図・report.md        │
 └─────────────────────────────────────────────────┘
                │  report/*.csv
                ▼
   tools/import_existing_results.py   → results/evals/*.json
   tools/make_metrics.py              → results/metrics.csv（★一括管理）
                │
                ▼
   tools/verify_deck.py   スライドの数値が metrics.csv と合っているか
```

**重い計算（推論）と、軽い集計を分けてある。** 推論結果は
`dc5-data/cache/analysis/` に残るので、集計や図だけ作り直すのは一瞬で済む。

## 1. analysis/ — タイル単位の再解析

### なぜ再推論するのか

ノートブックの出力には「条件全体のRecall/Precision/F値」しか残っていない。
それだと「どういうタイルで外しているのか」が分からない。
保存済みの重みで推論をやり直し、**1タイルずつ混同行列を取り直す**ことで、
タイルの性質（面積・傾斜・形）と誤りの関係を調べられるようにしている。

足し上げた値はノートブックの出力と F値 0.0001 以内で一致する
（`run_inference.py --verify` で確認できる）。

### run_inference.py

```bash
python analysis/run_inference.py --region all --verify
python analysis/run_inference.py --region hiroshima --conditions FinalFusion_SAM_APM
```

| 引数 | 意味 |
|---|---|
| `--region` | `hiroshima` / `hiroshima_bg` / `shimane` / `both` / `all` |
| `--conditions` | 条件名を並べる。省略すると全条件 |
| `--device` | `cuda` / `mps` / `cpu`。省略で自動 |
| `--force` | 既にCSVがあっても作り直す |
| `--verify` | ノートブック出力（ModelComparison）と突き合わせる |

**仕組みのポイント**

- 同じpklを使う条件はまとめて処理する（`config.group_by_pkl`）。
  5GBのpklを条件ごとに読み直すと時間が溶けるため、1地域あたり最大4回しか読まない
- 広島のテスト集合は、学習時と同じ `train_test_split(test_size=0.2,
  random_state=42)` を**インデックス配列に対して呼び直して**再現している。
  デュアル入力も単一入力も同じ引数なので、テストタイルは全条件で共通
- 出力は `dc5-data/cache/analysis/tiles/<条件>__<地域>.csv`。1行 = 1タイル

| 列 | 内容 |
|---|---|
| `tile_no` | タイル番号。条件をまたいで突き合わせるキー |
| `tp` `fp` `fn` `tn` | 通常評価の混同行列 |
| `tp_c` `fp_c` `fn_c` `tn_c` | 境界評価（中心96×96） |
| `gt_pos` `pred_pos` | 正解・予測の陽性画素数 |
| `prob_mean` `prob_pos_mean` `prob_max` | sigmoid 出力の統計 |

速度は MacBook(M4/MPS) で 50〜100 tiles/s。広島2,964枚が約45秒、
島根24,569枚が約6分。全条件×3地域で4〜5時間。

### run_features.py

```bash
python analysis/run_features.py --region all
```

モデルに依存しない、**タイルそのものの性質**を1行1タイルで出す。
地域ごとに1回でよい。傾斜は SAM のpkl（角度・度）から、起伏は pkl の
Max_H / Min_H から求める。

| 列 | 内容 |
|---|---|
| `gt_ratio` | 正解が占める画素の割合 |
| `gt_components` `gt_max_comp` | 正解の連結成分数・最大成分の面積 |
| `gt_compactness` | 周長 ÷ 面積。大きいほど細長い・複雑 |
| `gt_border_ratio` | 正解のうち境界16pxリングに掛かる割合 |
| `slope_mean` `slope_p90` `slope_max` | 傾斜角（度）の統計 |
| `slope_in_gt` `slope_out_gt` `slope_contrast` | 正解の内外の平均傾斜とその差 |
| `relief` | 起伏量（最大標高 − 最小標高, m） |
| `lon` `lat` | タイル左上の経度・緯度 |

地域を増やしたら `FEATURE_PKL` にその地域の SAM pkl を1行足す。
ここだけがコードの変更点になる。

### run_instance_eval.py

```bash
python analysis/run_instance_eval.py --region both --save-instances
```

警戒区域を「かたまり」単位で数える。**対応づけの方式を7通りまとめて評価する**
ので、しきい値を振り直すために推論をやり直す必要はない。

| 引数 | 意味 |
|---|---|
| `--connectivity` | 4 or 8 近傍（既定 8） |
| `--min-size` | これ未満のかたまりは数えない（既定 10 px） |
| `--prob-thr` | 二値化しきい値（既定 0.5） |
| `--save-instances` | 正解の箇所を1行ずつ書き出す |

方式の違いと、なぜ被覆方式を既定にしたかは `docs/箇所数評価_設計メモ.md`。
要点だけ書くと、IoU で1対1に対応づけると

- 近接した正解を1つの予測が飲み込んだとき、1個しかTPにできない
- 正解が小さいと、少しのずれで IoU が 0.3 を割る

の二重で損をする。実測で飲み込まれた正解が20.1%あり、
それらは IoU≧0.3 を 37.7% しか通らないのに被覆≧0.5 なら 89.9% 通る。

### run_attention.py

```bash
python analysis/run_attention.py --region hiroshima
```

Attention Gate の注意係数（0〜1）を取り出し、各段・各モダリティについて
「正解の内側と外側での平均の差」を測る。
「Attention を入れたのに精度が変わらない」のが
**注意が効いていないからなのか、効いているが精度に繋がっていないのか**を
切り分けるための材料。

`dc5lib/models.py` の `AttentionGate.coefficients()` と
`AttentionMultiEncoderUNet.forward(..., return_attention=True)` を使う。

### run_analysis.py

```bash
python analysis/run_analysis.py
```

推論結果を読んで、集計CSV・図・`report.md` を作る。**推論はしない**ので速い。
出力は `dc5-data/cache/analysis/report/` と `figures/`。

| 出力 | 内容 |
|---|---|
| `summary_by_condition.csv` | 条件ごとの micro（画素単位）/ macro（タイル平均）集計。tp/fp/fn も入る |
| `region_matrix.csv` | 地域 × テスト集合の作り方 を揃えた比較 |
| `matched_tileset_summary.csv` | 島根を「警戒区域ありのみ」に絞った再集計 |
| `paired_comparisons.csv` | 同じタイル上での条件どうしの差（Wilcoxon検定つき） |
| `stratified_f1.csv` | タイルの性質で層別した平均F値 |
| `error_decomposition.csv` | 見逃し/過検出の割合、境界リングへの誤差の集中度 |
| `instance_summary.csv` `instance_diagnostics.csv` | 箇所数評価 |
| `agreement_<地域>.csv` | 条件間のタイル別F値の相関 |
| `tile_difficulty_<地域>.csv` | タイルごとの全条件平均F値 |

図は16枚。条件の並び順は `ORDER` を使うが、**そこに無い条件は末尾に回す**ので、
新しい条件が黙って図から消えることはない。

### analysis/config.py

`dc5lib` からパスと条件を引く読み替え層。**条件のリストは持たない。**
以前はここに14条件を手で書いていて、モデルを増やすたびに
`experiments/` と2か所直す必要があった（片方を忘れると壊れる）。
いまは `experiments/*/config.yaml` が唯一の定義。

解析の中間生成物は数GBになるので、出力先はリポジトリではなく
`dc5-data/cache/analysis/` にしている。

## 2. tools/ — 記録と検査

### import_existing_results.py

```bash
python tools/import_existing_results.py --src <dc5-data>/cache/analysis
```

`report/*.csv` を読んで `results/runs/*.json` と `results/evals/*.json` を作る。
**解析結果（キャッシュ、使い捨て）と記録（git、永続）の橋渡し。**

| 引数 | 意味 |
|---|---|
| `--src` | 解析結果のフォルダ（`report/` を含む） |
| `--conditions` | 絞り込み。省略すると report に出てくる条件すべて |
| `--machine` `--when` | 評価を回した機械名・日時。省略すると現在のもの |

同じ測定（条件・地域・集合・評価軸・設定が同一）の古い記録は**自動で置き換わる**。
別のPCで評価し直すと `run_id` が変わるので、放っておくと
`metrics.csv` に同じ測定が2行並んでしまうため。

### make_metrics.py

```bash
python tools/make_metrics.py
```

`results/evals/*.json` を結合して `results/metrics.csv` を作り直す。
決定的な順序で書くので、どのPCで作っても同じ内容になる。
**git でコンフリクトしたら、手で直さずこれで作り直す。**

### verify_deck.py

```bash
python tools/verify_deck.py            # ずれている項目だけ
python tools/verify_deck.py --detail   # 全項目
python tools/verify_deck.py --slide res_fusion
```

発表スライドに埋め込んである数値が `results/metrics.csv` と合っているかを調べる。
**スライドのHTMLから数値を自動抽出して**突き合わせるので、
人が転記した一覧と比べることにはならない。

解析をやり直したり条件を足したりすると、スライドの数値だけが古いまま残る。
それを機械的に見つけるための検査。

再計算できない項目（タイル単位のCSVが要るもの）は「不可」として一覧に出し、
再生成のコマンドも表示する。黙って素通りさせない。

### check.py

```bash
python tools/check.py
```

コミット前の検査。異常があれば終了コード 1。

- 実験フォルダ名が大文字小文字だけ違っていないか（Ubuntu と Windows で壊れる）
- 同じパスが Unicode 正規化違い（NFC/NFD）で重複して追跡されていないか
- 図表に出す**表示ラベルが重複していないか**
- `config.yaml` の `name` がフォルダ名と一致しているか
- モデルクラスが `dc5lib/models.py` に登録されているか
- `forward` の引数の数と `inputs` の数が一致しているか
- `inputs` にある入力が pkl に含まれていそうか（ファイル名から推定）
- 重み（`.pth`）がリポジトリに紛れ込んでいないか
- `metrics.csv` が `evals/` と食い違っていないか
- 20MBを超えるファイルが追跡されていないか

**これらは全部、実際に一度踏んだ失敗から足した項目。**

### new_experiment.py

新しい条件の雛形を作る。使い方は `docs/練習_新しい条件を作る.md`。

### その他

| ファイル | 用途 |
|---|---|
| `migrate_to_dc5data.py` | 重み・データをSSDへ移す（実行済み。`--undo` で戻せる） |
| `rewrite_notebook_paths.py` | ノートブックのパスを dc5lib 経由に直す（実行済み） |
| `dataset_build/` | GeoTIFF から .pkl を作る一式。3チャネル対応 |

## 3. 典型的な使い方

### 新しい条件を学習したあと

```bash
python analysis/run_inference.py     --region all  --conditions <条件名>
python analysis/run_instance_eval.py --region both --conditions <条件名>
python analysis/run_analysis.py
python tools/import_existing_results.py --src <dc5-data>/cache/analysis --conditions <条件名>
python tools/make_metrics.py
python tools/check.py
```

`--conditions` で絞らないと、過去に記録済みの条件まで
今日の日時で上書きされる。新しい条件だけを指定すること。

### 集計のやり方だけ変えたいとき

```bash
python analysis/run_analysis.py      # 推論はやり直さない。数十秒
```

### スライドの数値を確かめたいとき

```bash
python tools/verify_deck.py --detail
```

### 全部やり直したいとき

```bash
python analysis/run_inference.py     --region all --force
python analysis/run_features.py      --region all --force
python analysis/run_instance_eval.py --region all --force --save-instances
python analysis/run_attention.py     --region hiroshima
python analysis/run_analysis.py
python tools/import_existing_results.py --src <dc5-data>/cache/analysis
python tools/make_metrics.py
```

外付けSSDが必要。全条件だと4〜5時間。

## 4. 設計のうえで気をつけていること

**条件のリストを2か所に持たない。** `experiments/*/config.yaml` が唯一の定義で、
`dc5lib/registry.py` が glob で拾う。モデルは増えていく前提なので、
中央の一覧を編集し忘れて壊れる作りを避けている。

**重い計算と軽い集計を分ける。** 推論結果はSSDのキャッシュに残し、
集計や図はそこから何度でも作り直せるようにしている。

**再現性のある値を記録に残す。** `results/` に入るのは git 管理下の軽いもの
だけで、タイル単位のCSV（数GB）はキャッシュに置く。
`metrics.csv` は生成物なので、衝突したら作り直す。

**壊れ方を先に捕まえる。** OS をまたぐと壊れるもの（大文字小文字、Unicode 正規化、
改行コード）、条件が増えると壊れるもの（ラベル重複、未登録のモデルクラス、
入力数の不一致）は `tools/check.py` で止める。
