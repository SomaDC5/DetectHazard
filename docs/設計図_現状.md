## 1. 層の構造 — どこが何を決めているか

```
  SSD (E:\dc5-data)                     リポジトリ
  ├── datasets/<Region>/*.pkl           dc5lib/            契約を持つ層
  ├── weights/<条件名>/best_model.pth    ├── paths.py       SSD の場所・重み・曲線の置き場
  ├── checkpoints/<条件名>/              ├── registry.py    config.yaml → Condition
  └── cache/analysis/                    ├── traincfg.py    config.train → TrainCfg（既定値つき）
                                         ├── models.py      arch 名 → クラス、build_model_for
  experiments/<条件名>/                   ├── losses.py      train.loss → criterion
  ├── config.yaml                        ├── inputs.py      3入力目の解決
  └── Keisya_airPhoto_final6.ipynb       ├── overlap.py     3x3 の貼り合わせ
        ↑ ここが実装。1,640行・40セル      └── data.py        pkl の読み込み

  analysis/*.py   評価（推論・箇所評価・和集合）    results/  evals/ curves/ metrics.csv
  tools/*.py      pkl を作る・条件を作る・検査する
```

**契約は `dc5lib` にあり、実装はノートブックにある。** 問題は
**ノートブックが契約をどれだけ使っているか**で、そこが条件ごとに違う。

### 1.1 自動で解決されているもの（55/55 本で例外なし）

| | 由来 |
|---|---|
| 重みの置き場 | `get(CONDITION).weights` → `E:\dc5-data\weights\<条件名>\best_model.pth` |
| 学習曲線の置き場 | `paths.curve_path(CONDITION)` → `results/curves/<条件名>.csv` |

**この2つだけは全条件で config 経由である。** だから条件名を変えれば
重みの行き先も変わる。逆に、**ノートブックの `CONDITION` が
フォルダ名と違えば別条件の重みを上書きする**（いまは全55本で一致。確認済み）。

`train:` の項目はこの1行を通る。**それが無ければ `epochs` も `lr` も

第3章・4.2 の中心の比較はここに入る。**論文で「設定はこうした」と
書くときの根拠は、config ではなくノートブックの直書きの行である。**

### 2.2 `bg_ratio` は55本すべてで直書きだった

いちばん分かりやすい例。`FinalFusion_SAM_APM_BLD_OverlapTrain` の

`bg30`（0.3）も `bg50`（0.5）も同じで、config の値はノートブックの値と
**手で合わせているだけ**である。

### 2.3 `両方`（経由と直書きが同居）はどこから来ているか

`dataset` の48本、`batch_size`・`test_size`・`random_state` の25本は、
**学習は config 経由なのに、同じノートブックに同居している

## 8. **アンサンブルにデータリークは無い**（2026-10-29 実測）

`random_state` が全条件で 42 でも、それだけでは足りない。
`train_test_split` が返すのは**添字**なので、**pkl のタイルの並びか
枚数が違えば、同じ添字が別のタイルを指す。** 和集合の構成員は
別々の pkl を読むので、ここは開いて確かめるしかない。

`tools/audit_splits.py` で各 pkl から `No` だけ取り出し、
ノートブックと同じ手順で分割して**タイル番号の集合**に直し、総当たりで
比較した。

| | 広島 | 島根 |
|---|---|---|
| 5つの pkl のタイル数 | **38,148**（全部同じ）| **24,569**（全部同じ）|
| `No` の指紋（sha256 先頭12桁）| **`e0230cf2d612`** | **`88a73375df63`** |
| 学習 / 検証 / テスト | 22,888 / 7,630 / 7,630 | 14,741 / 4,914 / 4,914 |
| **分割が食い違った組** | **0 / 10 組** | **0 / 10 組** |

`run_miss_overlap.py` の4本目（`OL_LogitHinge`）を入れた6本でも **0/6 組**。

> **和集合の再現率はデータリークで膨らんでいない。** `42`〜`44` の
> 床・天井・上限の数字は、構成員全員が**同一のテストタイル**で
> 測られたものである。

### 8.1 なぜここが崩れていなかったか

6本の分割コードは**1文字も違わない**。

    idx_all = np.arange(len(dataset2.No))
    idx_trainval, idx_test = train_test_split(idx_all, test_size=CFG.test_size,
                                              random_state=CFG.random_state)
    idx_train, idx_val = train_test_split(idx_trainval, test_size=CFG.val_size,
                                          random_state=CFG.random_state)

しかも各ノートブックが**自分で検算している**。添字の分割と配列の分割が
`No` で一致するかの assert 3本と、オーバーラップの近傍から検証・テストを
除いたうえで「テストが混入している」「検証が混入している」の assert 2本。

**そして `CFG` が無い29本は、どのアンサンブルにも入っていない。**
アンサンブルを作る所はリポジトリ全体で4ファイルだけで、構成員は
`STAGE1 + UNION3`（+ `BVB` / `BLD`）と `run_miss_overlap.py` の
`OL_LogitHinge` に限られる。

### 8.2 ただし旧プロトコルの3本は別の漏れを持つ

`Final_SAM_APM` / `Train_Hiroshima_Test_Shimane_OnlyDEM` / `OnlySAM` は
`8:2` で**検証分割が無い**。`修士論文の構成.md` のとおり
**テストのF値で最良エポックを選んでいる。**

これは和集合の漏れではなく**そのモデル自身の選択の漏れ**である
（テストを見て選んだ重みをテストで測っている）。
**アンサンブルには入っていないので `42`〜`44` には影響しない**が、

> **この3本は今後もアンサンブルに入れてはいけない。**
> 入れると、他の構成員のテストタイルをこの3本は学習に使っている
> （検証ぶんが学習に入っている）ため、和集合の意味が変わる。
> `6` の一覧に入れ、検査で止める（`設計図_修正案.md` の `5`）。

なお `OnlyDEM` / `OnlySAM` には `random_state` の無い
`train_test_split` が**コメントアウトされた形で**残っている。
有効な行は `random_state=42` である。**毎回ランダムではない。**
